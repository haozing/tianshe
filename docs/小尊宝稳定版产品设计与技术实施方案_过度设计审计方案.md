# 小尊宝稳定版产品设计与技术实施方案：过度设计审计方案

> 审计对象：`docs/小尊宝稳定版产品设计与技术实施方案.md`  
> 对象版本：v2.2 Gate 0 阻断修订版  
> 审计主题：识别方案中“必要稳定性设计”和“过度设计/过早设计”的边界  
> 审计日期：2026-06-29  
> 审计状态：方案级审计计划，可用于后续形成正式审计报告

## 1. 审计目标

本次审计不以“模块多就是过度设计”为判断标准，而是验证每一类复杂度是否有明确的业务风险、技术约束、验收证据和阶段价值支撑。

核心问题：

1. 现有方案是否把 MVP 交付前必须解决的问题和未来阶段问题混在一起。
2. Gate 0 到 Gate 4 的阻断项是否过多，是否会导致首个真实闭环迟迟无法落地。
3. 数据模型、JobEngine、Capability、规则包、更新、安全和测试体系是否存在提前实体化。
4. 哪些复杂度属于真实写操作、登录态隔离、崩溃恢复和敏感数据保护的必要成本。
5. 哪些设计可以降级为占位合同、Spike 产物、延后实现或可替换的薄封装。

## 2. 初步审计假设

基于当前文档的快速阅读，方案整体不像典型“无目标堆架构”，它的主线是稳定性、可恢复、凭据隔离和真实写操作安全，方向是成立的。

但存在局部过度设计风险，重点集中在：

| 风险点 | 初步判断 | 需要审计验证 |
|---|---|---|
| Gate 0 阻断项过多 | 高风险 | Runtime Spike、migration、API 合同、RuleService 骨架、完整首屏 API、脱敏 fixture 是否都必须在编码前完成 |
| P2/P3 能力提前实体化 | 中高风险 | 目录、Capability 元数据、逐功能规格是否只是规划，还是会提前形成代码负担 |
| 数据表一次性过多 | 中风险 | `xzb_update_history`、`xzb_rule_packages`、`xzb_session_check_events` 是否必须进入首版 migration |
| CapabilitySpec 字段过满 | 中风险 | P0/P1 是否需要完整 rateLimit、fixtures、reconcile、敏感字段等字段 |
| 更新体系设计偏重 | 中风险 | 插件更新是否应只保留 Gate 8 合同，首版只实现提示和规则包最小验签 |
| API 一次性完整注册 | 中风险 | Tianshe API 注入机制是否确实要求所有 API 先注册，还是可用稳定基础 API + capability 调度 |
| 测试门槛前置过多 | 中风险 | 哪些 contract test 是防事故必须，哪些可推迟到对应 Gate |

## 3. 审计范围

### 3.1 纳入范围

| 文档区域 | 审计重点 |
|---|---|
| 1-2 产品目标和非目标 | MVP 是否被稳定性目标扩大；非目标是否真的限制范围 |
| 3 ADR | 每个架构决策是否有可验证的必要性 |
| 4 总体架构 | 模块拆分是否超过首个闭环需要 |
| 5 插件实施形态 | 目录、manifest、构建合同是否提前固化未来实现 |
| 6 数据模型与迁移 | 首版表、索引、JSON envelope 和 Repository 合同是否过重 |
| 7 Runtime Gate | Spike 范围和阻断程度是否合理 |
| 8-10 登录、Profile HTTP、JobEngine | 稳定性底座是否可裁剪为最小可用闭环 |
| 11 API 与 Capability | API 面、Capability 元数据和确认模型是否过早泛化 |
| 12-13 16 个功能规格 | P2/P3 是否应停留在规划层，不进入首版实现合同 |
| 15 更新与规则配置 | 插件更新、规则热更新、host adapter 是否分层清晰 |
| 16-18 安全、脱敏、测试 | 安全测试是否按风险分阶段，而非一次性压入 Gate 0 |
| 19 实施路线 | Gate 划分是否能产出可验收增量 |

### 3.2 不纳入范围

- 不评估具体业务市场价值。
- 不审计抖店平台接口合法性和账号合规策略。
- 不替代 Runtime Spike、Profile HTTP Spike 或真实店铺验收。
- 不做源码级 bug 审查，除非某个设计必须依赖 Tianshe 源码事实。

## 4. 判断标准

### 4.1 必要复杂度

满足以下任一条件，倾向判定为必要复杂度：

| 标准 | 说明 | 文档中可能对应 |
|---|---|---|
| 防止不可逆副作用 | 避免重复删除、重复改价、重复营销创建 | previewHash、confirmToken、JobItem、Attempt、对账 |
| 保护凭据和敏感数据 | 防止 Cookie、token、收件信息泄露 | Profile 唯一凭据容器、脱敏 DTO、日志禁入字段 |
| 支持崩溃恢复 | 应用退出、断网、平台未知结果后能恢复 | JobEngine、RecoveryService、Artifact |
| 规避宿主不确定性 | Tianshe helper 或 Runtime 行为未稳定 | compatibility-adapter、Runtime Spike、contract test |
| 支撑首个闭环验收 | Gate 4 批量改标题真实写功能必须依赖 | Profile HTTP、规则固定、失败导出 |

### 4.2 过度设计

满足以下任一条件，倾向判定为过度设计：

| 类型 | 识别信号 | 处理方向 |
|---|---|---|
| 过早泛化 | 为 P2/P3 或未知功能实现通用框架 | 降级为文档合同或 feature placeholder |
| 过早实体化 | 当前 Gate 不使用但要编码、测试、迁移 | 延后到对应 Gate |
| 双重抽象 | 多层封装没有减少风险或复杂度 | 合并边界，保留一个稳定接口 |
| 阻断项膨胀 | 低风险能力阻塞 MVP 写闭环 | 改成非阻断验收或后置审计 |
| 配置先行 | 先设计热更新、远程规则、host adapter，但没有生产路径 | 保留静态配置和 Spike 问题 |
| 数据模型膨胀 | 表、索引、JSON envelope 覆盖未来能力 | 拆成 MVP migration 和后续 migration |
| 测试倒挂 | 测试矩阵远超当前可执行功能 | 按 Gate 分层，避免伪测试 |

## 5. 分级规则

| 等级 | 定义 | 建议动作 |
|---|---|---|
| OD-0 | 不是过度设计，是必要风险控制 | 保留，并补充验收证据 |
| OD-1 | 轻微超前，但成本低且能约束后续 | 保留为合同或注释，不要求完整实现 |
| OD-2 | 明显超前，会增加首版工程量 | 从当前 Gate 移出，延后到对应功能 Gate |
| OD-3 | 高成本且短期无收益，阻碍 MVP | 删除或改为 Spike / 待确认问题 |
| OD-4 | 与目标冲突，制造错误安全感 | 必须修订方案 |

## 6. 审计方法

### 6.1 复杂度库存盘点

为每个设计项建立库存表：

| 字段 | 填写要求 |
|---|---|
| 设计项 | 例如 Runtime Gate、JobEngine、RuleService |
| 所在章节 | 精确到章节或行号 |
| 当前 Gate | Gate 0-8 |
| 服务的首个用户场景 | 必须对应 MVP 闭环中的一步 |
| 不做的风险 | 明确事故类型或失败模式 |
| 当前实现成本 | 表、模块、API、测试、UI 的数量级 |
| 可替代方案 | 更小实现、手工流程或延后实现 |
| 审计判断 | OD-0 到 OD-4 |
| 建议动作 | 保留、收窄、后置、删除、补 Spike |

### 6.2 Gate 压力审计

逐一统计每个 Gate 的阻断项数量、可独立验收项数量和跨 Gate 依赖。

重点问题：

1. Gate 0 是否只包含“不做就无法安全开工”的内容。
2. Gate 1-4 是否能每个阶段交付可演示、可验收的增量。
3. Gate 5-8 是否只是规划，不应反向阻塞 Gate 0-4。
4. 是否存在“为了未来 16 个功能，把首个写功能复杂化”的情况。

建议输出：

| Gate | 当前阻断项 | 必要阻断项 | 可后置项 | 裁剪建议 |
|---|---|---|---|---|
| Gate 0 | 待审计填写 | 待审计填写 | 待审计填写 | 待审计填写 |
| Gate 1 | 待审计填写 | 待审计填写 | 待审计填写 | 待审计填写 |
| Gate 2 | 待审计填写 | 待审计填写 | 待审计填写 | 待审计填写 |
| Gate 3 | 待审计填写 | 待审计填写 | 待审计填写 | 待审计填写 |
| Gate 4 | 待审计填写 | 待审计填写 | 待审计填写 | 待审计填写 |

### 6.3 数据模型审计

审计问题：

1. 哪些表是批量改标题闭环必须的。
2. 哪些表只服务更新、规则热更新、诊断、未来营销或 P2/P3 能力。
3. JSON envelope 是否所有 JSON 列都必须首版强制。
4. DuckDB 事务能力不确定时，Repository 原子性合同是否过重或刚好必要。

建议分类：

| 表或机制 | MVP 必需 | 首版可选 | 后续 Gate | 判断 |
|---|---:|---:|---|---|
| `xzb_schema_migrations` | 是 | 否 | Gate 0 | 迁移基础 |
| `xzb_shops` | 是 | 否 | Gate 1 | 店铺绑定基础 |
| `xzb_shop_origin_sessions` | 是 | 否 | Gate 1 | 登录健康事实源 |
| `xzb_session_check_events` | 待定 | 是 | Gate 1/2 | 可能可作为诊断增强 |
| `xzb_operation_plans` | 是 | 否 | Gate 3 | 高风险预览确认 |
| `xzb_plan_jobs` | 待定 | 是 | Gate 3 | 仅大样本异步预览需要 |
| `xzb_jobs` | 是 | 否 | Gate 3 | 持久任务基础 |
| `xzb_job_shop_partitions` | 待定 | 是 | Gate 3/5 | 单店 MVP 可简化，多店写操作需要 |
| `xzb_job_items` | 是 | 否 | Gate 3 | 商品级失败隔离 |
| `xzb_job_item_attempts` | 是 | 否 | Gate 3 | 对账和证据 |
| `xzb_artifacts` | 是 | 否 | Gate 3 | 失败导出和诊断 |
| `xzb_rule_packages` | 待定 | 是 | Gate 4/8 | 可先用内置规则版本，热更新后置 |
| `xzb_update_history` | 否 | 是 | Gate 8 | 插件更新审计表，疑似可后置 |

### 6.4 API 面审计

审计问题：

1. 首屏是否真的需要一次性注册全部 API。
2. Tianshe 的 `context.exposeAPI` 是否只是不支持动态新增，还是可以注册稳定少量 API 后通过 `invokeCapability` 分发。
3. 每个 API 是否对应当前 Gate 的用户动作。
4. `checkForUpdates`、`retryFailedItems`、`getArtifacts` 是否应首版暴露，还是在对应 UI 出现后再暴露。

建议输出：

| API | 当前用途 | 首个使用 Gate | 是否首屏需要 | 建议 |
|---|---|---|---:|---|
| `getRuntimeStatus` | Runtime 状态 | Gate 0 | 是 | 保留 |
| `listCapabilities` | 能力列表 | Gate 0 | 是 | 保留 |
| `createShopBinding` | 新建店铺 | Gate 1 | 是 | 保留 |
| `createPlanJob` | 大样本预览 | Gate 3 | 否 | 可按 Gate 3 再启用 |
| `retryFailedItems` | 失败重试 | Gate 3/4 | 否 | 可保留合同，后置实现 |
| `checkForUpdates` | 更新检查 | Gate 8 | 否 | 疑似后置或只返回 unsupported |

### 6.5 Capability 泛化审计

审计问题：

1. `XzbCapability` 是否把 P3 营销、数据采集、商品批处理的差异都压成一个超大接口。
2. P0/P1 是否需要 `fixtures`、`rateLimit`、`reconcileStrategy`、`sensitiveFields` 等全字段。
3. 是否可以拆成 BaseCapability、WriteCapability、CollectCapability、MarketingCapability。

建议裁剪方向：

~~~ts
type BaseCapability = {
  name: string
  title: string
  version: string
  phase: "P0" | "P1" | "P2" | "P3"
  inputSchema: object
  outputSchema: object
  requiredOrigins: string[]
  sideEffectLevel: "none" | "low" | "medium" | "high" | "destructive"
}

type WriteCapability = BaseCapability & {
  previewItemSchema: object
  jobItemPayloadSchema: object
  confirmPolicy: "preview" | "typed_confirm"
  idempotencyKeyTemplate: string
  reconcileStrategy: "read_after_write" | "list_and_match" | "manual"
}
~~~

审计时只判断是否应该裁剪，不直接改设计。

### 6.6 更新和规则体系审计

审计问题：

1. 插件包更新是否已经明确依赖 Tianshe host adapter，不应在首版形成可执行承诺。
2. 规则包验签是否必须首版即实现，还是可以先使用内置规则版本加 hash。
3. `RuleService` 在 Gate 0 是“验签骨架”还是完整热更新。
4. `xzb_update_history` 是否应延后到 Gate 8。

建议判断：

| 设计项 | 可能结论 |
|---|---|
| 插件包自更新 | 首版只保留提示和 staging 校验，不进入 MVP 闭环 |
| 规则包热更新 | 若写操作依赖 endpoint 规则，可保留规则版本固定；热更新后置 |
| HostPluginUpdateAdapter | 保留为 Gate 8 外部合同，不做 Gate 0 阻断 |
| 更新验收 | 移到 Gate 8，Gate 0 只验 manifest 不越界 |

### 6.7 测试矩阵审计

审计问题：

1. Gate 0 测试是否只覆盖宿主合同、manifest、迁移、API 注入、脱敏边界。
2. 商品批量、数据采集、更新验收是否已经按 Gate 后置。
3. “每个 exposed API 必须有 contract test”是否会因为提前暴露 API 而制造大量空测。
4. 是否存在不能在当前阶段真实验证、只能伪造通过的验收项。

建议输出：

| 测试项 | 风险等级 | 当前 Gate | 建议 Gate | 原因 |
|---|---|---|---|---|
| Runtime 空值不透传 | 高 | Gate 0 | Gate 0 | 防止创建错误 Profile |
| 数据库错误脱敏 fixture | 高 | Gate 0 | Gate 0 | 防泄露 |
| 所有 API 成功路径 | 中 | Gate 0 | 分 Gate | 未实现能力不应伪测 |
| 更新失败旧版本恢复 | 中 | Gate 8 | Gate 8 | 不应阻塞 MVP |

## 7. 重点审计清单

### 7.1 必须优先确认的问题

1. Gate 0 是否可以缩为：插件可加载、manifest validator、Tianshe commit lock、Runtime Spike、adapter 合同、migration runner 最小表、API 注入最小合同、脱敏边界。
2. `xzb_rule_packages` 是否必须在首版 migration 中创建，还是 Gate 4 内置规则版本即可。
3. `xzb_update_history` 是否可以完全后置到 Gate 8。
4. `xzb_session_check_events` 是否可以由日志或 artifact 暂代，避免首版事件表。
5. `xzb_plan_jobs` 是否只在大样本预览真实需要时引入。
6. `JobShopPartition` 是否在首个真实写功能必须存在，还是单店 MVP 可先不启用但保留迁移。
7. Capability 是否需要统一大接口，还是分层接口更低成本。
8. `checkForUpdates()` 是否应从首屏 API 移出，或者只返回 `unsupported_by_host`。
9. P2/P3 的逐功能规格是否应保留为产品路线，不进入当前代码结构和测试。
10. “完整首屏 API 集合”是否等价于“所有未来 API”，如果是，需重新定义首屏范围。

### 7.2 明显不能轻易裁剪的设计

以下项目即使看起来复杂，也应先按必要复杂度处理：

| 设计 | 保留理由 |
|---|---|
| Profile 是唯一凭据容器 | 避免 Cookie/token 搬运和多店凭据污染 |
| Runtime Spike | Tianshe runtime 行为会影响登录、Profile 和平台识别 |
| compatibility-adapter | 宿主 API 类型和运行时差异需要收窄 |
| 高风险写操作预览和确认 | 批量改标题、改价、删除等都可能造成真实损失 |
| JobItem/Attempt | 支撑失败隔离、unknown_result、恢复和证据 |
| 脱敏 DTO 和错误脱敏 | 插件 API、日志、observation 都可能泄露敏感信息 |

## 8. 访谈和证据收集

### 8.1 需要向产品或业务确认

| 问题 | 影响 |
|---|---|
| 首个真实验收是否必须多店，还是单店即可 | 决定 `ShopPartition` 是否 MVP 必需 |
| 批量改标题首批商品规模上限 | 决定同步 preview、异步 plan job、分页和限流复杂度 |
| 是否必须首版支持规则远程更新 | 决定 `RuleService` 和 `xzb_rule_packages` 范围 |
| 是否存在生产插件更新通道 | 决定更新体系是否只保留提示 |
| 失败导出是否必须 Excel，还是 CSV 即可 | 决定 ArtifactService 首版范围 |

### 8.2 需要向工程确认

| 问题 | 影响 |
|---|---|
| Tianshe 是否提供事务或批量原子执行能力 | 决定 Repository 恢复设计复杂度 |
| `context.exposeAPI` 是否只能首屏静态注入 | 决定 API 注册策略 |
| Runtime Spike 两个候选的实现成本 | 决定是否两个都作为 Gate 0 阻断 |
| Profile HTTP 是否能在目标 origin 稳定执行 fetch | 决定写操作能否进入 Gate 4 |
| 插件包是否能生产签名安装 | 决定 Gate 8 更新路径 |

## 9. 审计步骤

### Step 1：建立复杂度清单

输出所有表、模块、API、Gate 阻断项、测试项、Spike 项和未来功能项，标记首个使用 Gate。

### Step 2：映射 MVP 闭环

将每个设计项映射到以下闭环：

~~~text
新增店铺
  -> 人工登录
  -> 登录检测
  -> origin 健康状态
  -> 导入商品
  -> 批量改标题 dry run
  -> 用户确认 previewHash
  -> 异步执行 job
  -> 查看进度
  -> 失败导出
  -> 重启后恢复
~~~

无法映射到该闭环的项目，默认进入“后置候选”。

### Step 3：按事故类型反推必要性

每个复杂设计必须对应至少一个事故类型：

| 事故类型 | 示例 |
|---|---|
| 凭据泄露 | Cookie/token 出现在 DB、日志、artifact |
| 重复写 | 重启后重复改标题、重复创建活动 |
| 未知结果 | 写请求断网后不知道是否成功 |
| 多店串扰 | A 店 Profile 或 origin 状态被 B 店使用 |
| 平台风控 | 验证码、短信、403、限流未能人工接管 |
| 宿主差异 | Tianshe Runtime 或 helper 行为和文档不一致 |

没有明确事故类型的项目，倾向 OD-2 以上。

### Step 4：提出裁剪版 Gate

形成两套路线：

1. 当前方案路线：保留原 Gate，用于安全优先。
2. 裁剪路线：只保留首个真实写闭环必须项，用于快速 MVP。

对比产出：

## 11. 初步可疑项清单

以下不是最终结论，只是首轮审计需要重点拆解的候选项：

| 候选项 | 疑似问题 | 审计方向 |

| `xzb_rule_packages` 首版建表 | 规则热更新可能早于真实需要 | 区分内置规则版本和热更新规则包 |
| `xzb_session_check_events` | 诊断价值高，但不一定是闭环必需 | 可改为日志或后置事件表 |
| `xzb_plan_jobs` | 大样本预览才需要 | Gate 3 再引入或首版仅在超预算时启用 |
| 完整 API 一次性注册 | 可能导致未实现 API 的空实现和空测试 | 重新定义“完整首屏 API” |
| Capability 大接口 | 所有能力共享同一超集字段 | 拆 Base/Write/Collect 分层 |

| 每个 exposed API 全量 contract test | 若 API 提前暴露会放大测试成本 | 按 Gate 激活测试 |

## 12. 预期结论形态

最终审计报告建议给出三段式结论：

1. **总体判断**：方案是否存在过度设计，以及严重程度。
2. **保留底座**：哪些复杂度是稳定版必须付出的成本。
3. **裁剪清单**：哪些内容从 Gate 0-4 移到后续 Gate，哪些改成 Spike 或待确认问题。

建议最终结论使用如下格式：

~~~text
本方案存在局部过度设计，但不是整体方向错误。

必须保留的是：Profile 凭据隔离、Runtime Spike、adapter 合同、预览确认、JobItem/Attempt、恢复和脱敏边界。

建议裁剪的是：首版更新发布实体化、P2/P3 能力提前代码化、Capability 超集字段、部分诊断/规则热更新表、全量 API 提前注册和全量 contract test。
~~~
