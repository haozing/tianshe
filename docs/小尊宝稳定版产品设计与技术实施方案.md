# 小尊宝稳定版产品设计与技术实施方案

> 版本：v2.3 稳定便利修订版  
> 日期：2026-06-29  
> 状态：可作为 Gate 0 工程基线；阶段 0 先完成依赖锁定、插件壳、显式 Runtime、登录/只读闭环和最小 migration。真实批量写操作在对应 Runtime 写能力、plan/job 合同和规则版本固定通过前不得开放。  
> 适用范围：基于 Tianshe 插件体系重写小尊宝抖店工具箱，目标是获得更稳定、可恢复、可验收、可分阶段上线的桌面端白牌实现。

## 1. 文档控制



### 1.2 基线约束

进入编码前必须确认：

| 项 | 约束 |
|---|---|
| Tianshe 版本 | 阶段 0 锁定一个 commit 或 tag，并在本文档附录记录 |
| 插件目录 | 开发期放在 Tianshe 支持的 plugins 或 js-plugins 目录下，最终以 zip 安装 |
| 状态库 | 核心业务状态由 xzb_ 前缀表和 migration 管理 |
| Profile | 一个店铺绑定一个 Profile，Profile 是长期登录态事实源；业务库不保存 raw Cookie/token |
| Runtime | 一个 Profile 固定一个显式 Runtime；Gate 0 可用 `electron-webcontents` 创建 Profile、登录和只读验证；真实写操作要求对应 Runtime 写能力通过最小验证；适配层禁止把空 runtimeId 传入 Tianshe helper |
| Cookie/下载便利 | 允许 ProfileHttpService 或 DownloadService 在单次请求内临时读取当前 Profile 的 Cookie header，用于平台下载、导出结果拉取或只读验证；不跨店、不跨 Runtime、不持久化、不写入任务事实源 |
| 高风险写操作 | 必须先生成预览，再签发确认，再异步提交 job |
| MCP/跨插件 | MVP 不开放写操作；默认 mcpCallable 为 false |
| UI API | manifest 的 crossPlugin 只做授权声明，真实 API 必须由 context.exposeAPI 注册 |
| 发布与规则 | 首版不实现插件包自更新、update manifest、staging 安装或完整规则包热更新；内置规则随安装包发布；Gate 2/4 可引入 Hotfix Lite 远程 JSON 配置，仅覆盖 endpoint、错误码和字段映射，必须有本地兜底、last-known-good 缓存和 job 版本固定；禁止远程可执行 JS |

### 1.3 术语

| 术语 | 定义 |
|---|---|
| ShopBinding | 小尊宝内部店铺绑定记录，主键为 shopRecordId |
| Account | Tianshe Account，记录平台账号元信息和 Profile 关联 |
| Profile | Tianshe BrowserProfile，长期凭据事实源 |
| OriginSession | 某个店铺在 fxg、compass、buyin 等 origin 上的登录健康状态 |
| LoginSession | 人工登录窗口的服务端会话，持有 PopupBrowserHandle |
| OperationPlan | 高风险或批量操作的预览计划 |

| confirmToken | 一次性确认凭证的实现别名，绑定 previewHash；用于防重复提交和保证预览一致性，不作为主要安全边界 |
| Job | 一次提交后的父任务 |
| ShopPartition | 多店任务中某个店铺的子任务分区 |
| JobItem | 单商品、单订单、单活动或单指标的执行明细 |
| Attempt | JobItem 的一次请求或一次页面动作尝试 |
| Artifact | 导出文件、失败包、截图、诊断包等可追溯产物 |
| RulesVersion | endpoint、错误码、业务规则的内置配置版本 |

## 2. 产品目标

### 2.1 目标用户

小尊宝稳定版服务多店铺抖店运营人员，帮助他们在一个桌面工具内完成：

- 店铺绑定、分组、登录状态管理和人工接管。
- 商品批量上下架、删除、达人秀、改标题、改价、运费模板处理。
- 经营、资金、售中、违规等多店数据采集和导出。
- 限时限量购、新人礼金、通用优惠券等营销工具。
- 商机提报和清理滞销。
- 任务进度、失败导出、重试、取消和崩溃恢复。

### 2.2 MVP 稳定闭环

首个可交付闭环固定为：

~~~text
新增店铺
  -> 打开抖店人工登录
  -> 复用登录窗口检测登录
  -> 建立 origin 级健康状态
  -> 导入商品
  -> 批量改标题 dry run
  -> 用户确认 previewHash
  -> 异步执行 job
  -> 任务中心查看进度
  -> 失败项导出
  -> 应用重启后任务状态可恢复
~~~

MVP 不要求一次性还原全部 16 个功能，但所有功能必须落在同一个登录、任务、数据、确认、失败和规则版本模型里。

### 2.3 稳定性目标

| 目标 | 可验收要求 |
|---|---|
| 登录稳定 | 一个店铺一个 Profile，关闭登录窗口和重启应用后登录态仍在 Profile 中 |
| 无 lease 自锁 | 登录窗口打开时点击检测不会排队卡死，关闭窗口后 lease 必须释放 |
| 状态唯一 | 业务只读取 xzb_shop_origin_sessions；框架 ProfileLoginState 只作为可选同步 |
| 任务持久 | 所有副作用前先落 job、partition、item 和 attempt |
| 可恢复 | 启动时扫描非终态任务，进入恢复、对账或人工确认 |
| 不重复写 | 重试和恢复必须受 idempotencyKey、previewHash 和平台对账约束 |
| 失败隔离 | 单商品、单指标、单店失败不扩散到其他 item 或店铺 |
| 用户接管 | 验证码、短信、2FA、风控、未知结果都能引导人工处理 |
| 规则确定 | 一个 job 固定 pluginVersion、rulesVersion、endpointVersion |
| 版本确定 | 首版规则配置随插件包发布；运行中的 job 固定 pluginVersion、rulesVersion、endpointVersion |
| 证据可查 | 每个 attempt 有脱敏 evidence、错误分类、耗时和关联 artifact |
| 便利热修 | endpoint、错误码和字段映射可通过 Hotfix Lite JSON 快速修复；失败时回退内置规则或 last-known-good，不阻断已固定版本的 job |
| 敏感最小化 | 不把 raw Cookie、token、完整请求头、完整收件信息写入业务库、日志或 artifact；单次请求内的临时 Cookie 桥接只服务当前 Profile 操作 |

### 2.4 非目标

首版明确不做：

- 不自动绕过验证码、短信验证、2FA 或风控。
- 不把完整 Cookie、token 或浏览器缓存导出到业务数据库。
- 不在不同 Runtime 或不同 Profile 之间搬登录态。
- 不把抖店 SDK 或小尊宝业务规则塞进 Tianshe core。
- 不开放 MCP、HTTP 或跨插件高风险写操作。
- 不使用远程可执行 JS、CSS 或插件包承载核心业务逻辑。
- 不做插件包自更新、update manifest、staging 安装或完整规则包热更新；Hotfix Lite JSON 配置是允许的便利修复通道。
- 不做完整云插件市场。
- 不承诺在 Runtime 写能力验证前真实执行抖店批量写接口。

## 3. 架构决策

### 3.1 ADR-001：单插件承载

稳定版首版采用一个插件：

~~~text
xzb_toolbox
~~~

原因：

- 16 个功能共享店铺、Profile、任务、失败导出和规则版本模型。
- 单插件更容易保证状态迁移和版本一致。
- 后续拆分插件前，需要先稳定 Capability 合同。

### 3.2 ADR-002：Profile 是长期凭据事实源

所有 Cookie、localStorage、IndexedDB、平台登录状态长期只存在 Tianshe Profile 的浏览器存储中。业务库只记录店铺、Profile、Runtime、origin 登录健康和任务事实，不保存 raw Cookie/token。

允许的便利桥接：

- ProfileHttpService 或 DownloadService 可在一次受控请求内临时读取当前 Profile 的 Cookie header。
- 桥接仅用于当前 shopRecordId、当前 runtimeId、当前 origin 的下载、导出拉取、只读验证或平台接口请求。
- 临时 Cookie 不返回 UI，不写库，不进入日志、artifact、evidence 或任务 payload。
- 桥接失败时必须返回可分类错误，不能把 Cookie 复制到别的 Profile、Runtime 或通用 HttpClient 池。

禁止：

- 保存 raw Cookie 字符串。
- 保存 token 字段到业务表。
- 把 WebContents Cookie 搬运成长期 HttpClient 会话。
- 将一个店铺凭据复制到另一个 Runtime。

### 3.3 ADR-003：核心状态不用空 dataTables

Tianshe dataTables 适合展示型数据集，但任务状态、迁移、attempt 和 artifact 需要事务、约束、恢复和跨表一致性。因此核心状态使用插件自管 xzb_ 表：

~~~text
helpers.database.executeSQL
  -> XzbDatabaseRepository
  -> xzb_schema_migrations
  -> xzb_shops
  -> xzb_shop_origin_sessions
  -> xzb_jobs
  -> xzb_job_shop_partitions
  -> xzb_job_items
  -> xzb_job_item_attempts
  -> xzb_artifacts
~~~

dataTables 后续只用于只读投影或运营报表，不承载核心状态。

### 3.4 ADR-004：Runtime 显式固定，写操作先验证

Tianshe 源码声明的 BrowserRuntimeId 包含：

| Runtime | 小尊宝首版处理 | 原因 |
|---|---|---|
| electron-webcontents | Gate 0 默认登录/只读 Runtime；真实写能力需要最小验证 | 应用内登录体验最好，Profile 持久化稳定，依赖最低 |
| chromium-extension-relay | Electron 失败或需要 response body/扩展能力时的新 Profile 兜底 | 外部 Chrome/扩展能力更强，但体验和安装成本更高 |
| firefox-bidi | 源码支持，但 MVP 不默认启用 | 需要额外浏览器下载、平台兼容性和能力矩阵验证 |
| chromium-cloak-playwright | 源码支持，但 MVP 不默认启用 | 需要额外 provider、风控表现和发布体积验证 |

阶段 0 不再把 Runtime 写能力验证作为“所有店铺接入”的阻断项。小尊宝可以使用显式 `electron-webcontents` 创建 Profile、打开人工登录窗口和执行只读验证；这直接服务便利性和首个闭环。

Runtime Gate 的真实边界是写操作：

- `runtime.default` 必须是显式值，首版可为 `electron-webcontents`，不得依赖 Tianshe 对空值的归一化。
- `compatibility-adapter.ts` 在调用 `helpers.profile.create()` 前必须把 runtimeId 归一为本项目允许的显式值，并拒绝 `""`、`undefined`、`null` 或未知字符串继续传给 Tianshe。
- `createShopBinding` 在 Gate 0 可创建显式 Electron Profile，返回的店铺状态必须包含 `runtime_id_snapshot` 和 `runtimeWriteStatus = "pending" | "passed" | "failed"`。
- `ProfileHttpService` 只读请求可在登录/只读验证通过后使用；真实写请求必须检查当前 Runtime 对应 capability 的 `runtimeWriteStatus = "passed"`。
- Electron 写能力验证失败时，不迁移凭据；用户通过 Runtime 迁移向导新建 `chromium-extension-relay` Profile 并重新登录。

Tianshe 当前实现会把空值、缺失值或非法 BrowserRuntimeId 归一到宿主默认 Runtime。小尊宝不能依赖“空字符串”等价于未配置。`compatibility-adapter.ts` 的 contract test 必须覆盖：

- 空 runtimeId 不会传入 Tianshe Profile helper。
- 显式 `electron-webcontents` 可创建登录/只读 Profile。
- 写能力验证 pending/failed 时，`submitJob` 或写型 capability 返回标准错误 `RUNTIME_WRITE_VALIDATION_REQUIRED`。
- 既有 Profile 禁止原地更新 runtimeId。

### 3.5 ADR-005：长任务全部异步化

UI 不直接调用会跑完整批处理的万能执行入口。所有批量或高风险能力使用：

~~~text
createPlan
  -> getPlan
  -> confirmPlan
  -> submitJob
  -> getJob / subscribeJobEvents
  -> exportJobFailures
~~~

同步 API 只用于列表、状态查询和短只读请求。

`createPlan` 也必须受执行预算约束：

- 小样本 bounded preview 可同步返回，必须满足 capability 声明的 `maxSyncItems` 和 `maxSyncDurationMs`。
- 大店、多店、跨 origin 或预计超过预算的预览必须走异步计划任务：`createPlanJob -> getPlanJob -> getPlan`。
- `confirmPlan` 只能确认已完成且 `previewHash` 未变化的 plan。

|---|---|---|

### 4.3 信任边界

| 边界 | 信任策略 |
|---|---|
| UI 到 API | 本机插件页面可调用，所有入参仍做 runtime schema 校验 |
| API 到 JobEngine | 高风险能力必须先有 confirmed plan |
| Plugin 到 Tianshe helpers | 通过 adapter 层访问，锁定版本后再实现 |
| Plugin 到平台页面 | 只在 Profile browser 内请求，凭据不导出 |
| Rules config | 内置规则随插件包发布；Hotfix Lite JSON 可选开启，启动时做 schema、hash、host allowlist、缓存回退校验 |

### 5.2 manifest 首版

首版 manifest 不声明空 dataTables，不开放 MCP 写操作。

以下 manifest 中的 `runtime.default` 是登录/只读路径的显式默认值。真实写操作不因为该默认值存在而自动开放，必须另看 Runtime 写能力验证状态。

Manifest validator 是 Gate 0 阻断项，必须在 package smoke test 中执行：

- `contributes.activityBarView.source.type` 必须为 `local`，小尊宝首版禁止 `remote` UI 源。
- `source.path` 归一化后必须仍位于插件包目录内，禁止 `../`、绝对路径、符号链接跳出插件包。
- 核心 ActivityBar 页面使用本地资源；不允许加载远程可执行 JS、CSS、HTML 承载核心业务逻辑。
- `runtime.default` 必须是显式合法值；如安装环境配置缺失，adapter 使用项目默认 `electron-webcontents` 补齐后再调用 Tianshe，仍不得传空值。

        "strategy": "keep-alive"
      },
      "isolation": {
        "contextIsolation": true,
        "enableNodeIntegration": false
      }
    }
  }
}
~~~

说明：

- Tianshe 当前源码支持 `electron-webcontents`、`chromium-extension-relay`、`firefox-bidi`、`chromium-cloak-playwright`。小尊宝 MVP 默认用 `electron-webcontents` 完成登录和只读验证；写能力验证失败或需要扩展能力时，新建 `chromium-extension-relay` Profile 兜底；后两者必须在 Runtime 报告中明确记录为“源码支持但首版排除”或经评审纳入候选。

## 6. 数据模型与迁移

### 6.1 原则

- 核心状态表使用 xzb_ 前缀，由 migration runner 创建和升级。
- 每次插件 activate 先执行 schema 校验，失败则只开放只读诊断 API。
- 对外 API 使用 shopRecordId，不让 UI 直接操作 accountId、profileId。
- 每个 job 固定 pluginVersion、rulesVersion、endpointVersion。
- 核心可演进 JSON 字段必须带 schemaVersion；简单列表 JSON 可先使用 repository 字段校验，不把全量 envelope 作为 Gate 0 阻断项。
- JSON 字段必须使用 Repository 层 schema 校验写入，不允许 Service 直接拼装裸对象写库。DuckDB 的 JSON 类型不承担 schemaVersion 约束。
- 不保存 raw Cookie、token、完整请求头、完整响应正文；单次请求 Cookie 桥接不得写入任何 JSON 字段。
- 导出文件、截图和诊断包作为 artifact 管理，记录 hash 和脱敏状态。

核心 JSON envelope 格式：

~~~ts
type XzbJsonEnvelope<T extends object> = {
  schemaVersion: string
  data: T
}
~~~

`input_json`、`preview_json`、`evidence_json`、`payload_json`、`response_summary_json`、`metrics_json` 等会跨版本演进或进入任务恢复的 JSON 列必须写入该 envelope。`shop_record_ids_json`、简单筛选条件和展示偏好可使用固定 schema 校验。Repository contract test 按对应 Gate 覆盖缺失 `schemaVersion`、未知 `schemaVersion`、额外敏感字段；Gate 0 只要求最小登录/店铺表的读写和向后兼容测试通过。

### 6.2 Migration runner

启动流程：

~~~text
activate()
  -> init ConfigService
  -> runMigrations()
  -> verifySchemaVersion()
  -> loadBundledRuleConfig()
  -> recoverInterruptedJobs()
  -> exposeAPI()
~~~

迁移表：

| 字段 | 类型 | 说明 |
|---|---|---|
| version | VARCHAR PRIMARY KEY | 迁移版本，例如 001_initial |
| description | TEXT | 迁移说明 |
| checksum | VARCHAR | migration 内容 hash |
| applied_at | BIGINT | 应用时间，Unix ms |
| plugin_version | VARCHAR | 应用迁移的插件版本 |

Migration runner 合同：

- 插件侧只允许 `XzbDatabaseRepository` 调用 `helpers.database.executeSQL(sql)` 执行主库 SQL，不传 `datasetId`；业务 Service、JobEngine、Capability handler 不得直接调用 database helper。
- 每个 migration 是单 SQL 数组，逐条执行，避免多语句 SQL。
- `checksum = sha256(version + description + upSql.join("\n"))`，已应用 migration 的 checksum 不匹配时进入只读诊断，不自动修改。
- 执行前先创建 `xzb_schema_migrations`，执行后写入 version、description、checksum、applied_at、plugin_version。
- DDL 必须幂等；DuckDB 无法可靠表达的唯一性和外键约束，必须在 Repository 层使用条件更新、唯一索引或事务等价逻辑兜底。
- 关键索引、状态枚举和应用层唯一性规则必须随 migration 一起提交，不能只写字段表。
- `helpers.database.executeSQL` 抛出的错误可能包含 SQL 或 params。Repository 必须捕获并重新抛出 `XzbDatabaseError`，只保留 `operation`、`errorCode`、`safeMessage`、`correlationId`，不得把 SQL、params、Cookie、Authorization、完整请求头或平台响应正文传出 API 边界。
- Gate 0 必须保证 Repository 捕获数据库错误并只返回 `safeMessage`、`errorCode`、`correlationId`。完整数据库错误脱敏 fixture 在 Gate 2/3 随 exposed API、evidence、artifact 一起补齐，不阻断店铺登录闭环。
- 若锁定的 Tianshe commit 未提供插件级 transaction API，所有跨表状态变更必须拆成可恢复的单语句步骤，并通过状态机、幂等键和恢复扫描完成最终一致；不得在文档或代码中假设存在隐式事务。

首版 migration 最小清单见附录 A。

### 6.2.1 XzbDatabaseRepository 原子性合同

`XzbDatabaseRepository` 是唯一持久化入口。方法按 Gate 渐进实现，后续 Service 只能调用 Repository 暴露的产品语义方法：

| Gate | 方法 | 原子性要求 |
|---|---|---|
| Gate 0 | `applyMigrationStep(step)` | 单语句执行；失败后 migration 状态进入只读诊断 |
| Gate 0 | `createShopBindingSagaStep(step)` | 每步幂等；失败补偿只删除本次创建且未激活的 Account/Profile 绑定 |
| Gate 0 | `upsertOriginSession(session)`、`listShops(filter)` | 店铺和 origin session 读写只以 xzb_ 表为事实源 |
| Gate 3/4 | `confirmPlan(planId, previewHash, confirmContext)` | 条件更新把 `ready -> confirmed`，绑定 previewHash、inputHash、ruleConfigHash 和过期时间 |
| Gate 3/4 | `createJobFromConfirmedPlan(planId)` | 使用 `planId + previewHash + ruleConfigHash` 幂等创建 job，重复提交返回既有 jobId |
| Gate 3/4 | `claimJobItem(workerId, now)` | 单语句条件更新 `pending/retryable -> running`；affected rows 必须为 1 |
| Gate 3/4 | `finishAttemptAndItem(attemptId, result)` | 先写 attempt 终态，再以条件更新推进 item；恢复扫描能修正中间态 |
| Gate 3/4 | `cancelJob(jobId)` | 只把未开始或可中断项置为 cancelled；已产生副作用项保持可对账状态 |

所有会产生副作用的方法必须有“重复调用、进程中断后恢复、affected rows = 0”测试。写链路方法未通过前不得开放真实写接口；Gate 0 登录链路不被后续 job 方法阻断。

### 6.12 内置规则配置与 Hotfix Lite

首版不创建 `xzb_rule_packages` 和 `xzb_update_history`，也不实现完整规则包热更新流程。endpoint 映射、错误码映射和业务规则默认随插件包发布，由 `RuleConfigService` 在启动时加载并校验：

- schemaVersion 合法。
- `rulesVersion`、`endpointVersion` 和 `ruleConfigHash` 可计算、可记录。
- endpoint host 命中固定 allowlist。
- endpoint path 模板合法，不允许任意完整 URL。
- 规则配置只包含 JSON 数据，不包含 JS 代码或风控绕过逻辑。

为保留平台接口变化后的修复便利性，Gate 2/4 可引入 Hotfix Lite：

- 只允许远程 JSON 配置覆盖 endpoint path、错误码映射、字段映射和响应 schema hash。
- 配置来源必须是固定 URL 或固定 host 下的固定路径，不能让服务端下发任意 URL。
- 启动失败、下载失败、schema 不兼容或 hash 不匹配时，回退 last-known-good；没有 last-known-good 时回退随包内置规则。
- 每次创建 plan/job 时固定 `rule_config_hash`、`rulesVersion`、`endpointVersion` 和 `config_source = "bundled" | "hotfix-lite"`。
- 已运行 job 永远读取创建时绑定版本，不受后续 Hotfix Lite 更新影响。

`submitJob` 创建 job 时必须写入 `rule_config_hash`、`rules_version` 和 `endpoint_version`。执行 item 时只读取 job 绑定版本，运行中的 job 不受后续插件包升级或配置变更影响。

| compatibility-adapter.ts | 插件访问 Tianshe helper 和 context API 的唯一入口 |
| runtime-validation-report.md | Electron 登录/只读验证、写能力验证状态、Extension 兜底和源码已支持但首版排除 runtime 的结论 |

Tianshe 当前源码存在运行时实现和公开类型声明不完全一致的情况：`context.exposeAPI(map)` 在运行时可用，但公开 `PluginContext` 类型可能没有该方法或签名不一致。小尊宝业务代码不得直接依赖 Tianshe 原始类型；必须通过 `compatibility-adapter.ts` 固化本项目使用的最小合同。

~~~ts
type XzbExposedApiMap = Record<string, (...args: unknown[]) => Promise<unknown> | unknown>

type XzbPluginContext = {
  exposeAPI(apiMap: XzbExposedApiMap): void
}

type XzbHelpers = {
  profile: unknown
  account: unknown
  savedSite: unknown
  database: unknown
  storage: unknown
  taskQueue: unknown
}
~~~

Gate 0 必须包含一条 contract test：使用锁定的 Tianshe commit 编译 `activate(context, helpers)`，并验证 `context.exposeAPI({ getAppStatus })` 在 ActivityBar 页面收到 `pluginAPIReady` 后可调用。

`compatibility-adapter.ts` 还必须把 Tianshe helper 收窄成小尊宝允许的产品语义。源码允许但小尊宝禁止的能力不得透传：

- 禁止业务代码直接访问 `rawHelpers.profile`、`rawHelpers.account`、`rawContext`。
- `createProfileForShop(input)` 必须要求显式 runtimeId；登录/只读可使用项目默认 `electron-webcontents`，写型 capability 另行检查 runtime write validation。
- 不暴露通用 `profile.update(profileId, patch)`；若后续必须更新 Profile 元信息，只能提供白名单方法，并明确拒绝 `runtimeId`、`fingerprintSource`、`runtimeSourceOverride` 等会改变运行时或指纹来源的字段。
- Runtime 迁移只能调用 `createProfileForRuntimeMigration()` 创建新 Profile，再由 ShopService 重新绑定 Account/ShopBinding。
- Contract test 必须断言 adapter 不存在可调用的 `updateProfileRuntime`、`rawProfileUpdate` 或等价逃逸口。

### 7.3 Runtime 验证清单

使用测试店铺验证：

| 场景 | Gate | electron-webcontents | chromium-extension-relay | 通过标准 |
|---|---|---|---|---|
| 抖店人工登录 | Gate 0 | 必测 | Electron 失败时必测 | 登录成功并重启保持 |
| fxg 首页识别店铺 | Gate 0 | 必测 | Electron 失败时必测 | 能获取 shopId、shopName |
| 商品详情预览/只读验证 | Gate 2 | 必测 | 需要 response body 时必测 | Profile 内请求成功 |
| 文件下载 | Gate 2 | 必测 | 必测 | artifact 可落盘，必要时使用一次性 Cookie 桥接 |
| 风控/验证码识别 | Gate 2 | 必测 | 必测 | 能返回人工接管状态 |
| 批量改标题低风险样本 | Gate 4 前 | 必测 | Electron 写验证失败时必测 | 真实接口返回可分类，失败不重复写 |
| 批量改价预览 | Gate 5 前 | 必测 | 可选 | SKU 信息完整 |
| 罗盘 origin 激活 | Gate 6 前 | 必测 | 必测 | compass session 可检测 |

Electron 登录/只读验证失败时：

- 新建 Profile 默认 Runtime 改为 `chromium-extension-relay`。
- 已登录 Electron Profile 不迁移凭据。
- 用户通过 Runtime 迁移向导新建 Profile 并重新登录。

Electron 写能力验证失败时：

- 已登录 Electron Profile 仍可继续登录、只读、导出和诊断。
- 写型 capability 入口显示“需要 Runtime 写验证/迁移”，不创建真实写 job。
- 用户可为该店新建 `chromium-extension-relay` Profile 并重新登录，验证通过后再开启写能力。

### 7.4 Runtime 迁移向导

不在设置页提供“原地切换 Runtime”。迁移流程必须是：

~~~text
选择店铺
  -> 创建新 Profile(runtimeId = target)
  -> 创建或更新 Account 指向新 Profile
  -> 新增 pending_login ShopBinding
  -> 用户重新登录
  -> verify 成功并识别同一 shopId
  -> 旧绑定 archived
~~~

禁止实现：

- 在既有 Profile 上调用 `helpers.profile.update(profileId, { runtimeId })`。
- 复制 Cookie、localStorage、IndexedDB、扩展存储或任何凭据到新 Runtime。
- 让 UI 暴露 `profileId` 后由前端选择 Runtime。

## 8. 登录与会话方案

### 8.1 登录模型

~~~text
xzb_shops
  -> Tianshe Account
  -> Tianshe Profile
  -> xzb_shop_origin_sessions[fxg, compass, buyin]
  -> xzb_session_check_events
~~~

业务状态只读取 xzb_shop_origin_sessions。shops 表只保存绑定和展示摘要。

### 8.2 新增店铺 Saga

~~~text
createShopBinding(name, runtimeId)
  -> ensureDoudianSavedSite(name = 抖店, url = https://fxg.jinritemai.com)
  -> helpers.profile.create({ name, runtimeId })
  -> helpers.account.create({ profileId, platformId, name, loginUrl })
  -> insert xzb_shops(binding_status = pending_login)
  -> return shopRecordId
~~~

补偿：

| 失败点 | 补偿 |
|---|---|
| Profile 创建失败 | 直接返回失败 |
| Account 创建失败 | 删除刚创建的 Profile，失败则记录诊断 |
| xzb_shops 插入失败 | 删除 Account，删除 Profile，失败则记录诊断 |
| 登录后发现重复 shopId | 新绑定置 duplicate，不执行任务 |

### 8.3 LoginSessionController

职责：

- 每个 shopRecordId 同时最多一个人工登录窗口。
- 打开窗口时保存 PopupBrowserHandle，不把 handle 传给 UI。
- UI 只拿 loginSessionId。
- 检测登录时复用 popup 当前 browser。
- 关闭、超时、插件 deactivate、应用退出时必须 release。

状态机：

~~~text
idle
  -> opening
  -> awaiting_user
  -> verifying_on_same_popup
  -> logged_in
  -> released

awaiting_user
  -> captcha
  -> two_factor
  -> blocked
  -> needs_manual_login
  -> closing
  -> released
~~~

API：

| API | 说明 |
|---|---|
| openLogin(shopRecordId) | 打开或返回已有登录会话 |
| getLoginSession(loginSessionId) | 查询窗口状态 |
| verifyLoginSession(loginSessionId, origins) | 复用 popup browser 检测 |
| closeLoginSession(loginSessionId) | 关闭窗口并释放 handle |

verifyLoginSession 不允许调用同 Profile 的 withLease。

### 8.4 登录检测

检测流程：

~~~text
verifyLoginOnBrowser(browser, shopRecordId, origins)
  -> navigate fxg homepage
  -> site adapter 判断页面状态
  -> page fetch 店铺信息接口
  -> 解析 shopId、shopName、secShopId
  -> 检查重复绑定
  -> upsert xzb_shop_origin_sessions
  -> insert xzb_session_check_events
  -> 返回结构化状态
~~~

状态枚举：

| 状态 | 含义 | 后续动作 |
|---|---|---|
| logged_in | 当前 origin 已验证 | 可以继续 |
| needs_manual_login | 未登录或登录页 | 打开登录窗口 |
| captcha | 验证码或滑块 | 人工接管 |
| two_factor | 短信或二次验证 | 人工接管 |
| blocked | 风控或封禁 | 停止该店任务 |
| expired | 曾登录但已过期 | 重新登录 |
| unknown | 无法判断 | 记录证据并人工复核 |

### 8.5 ensureSession

所有业务能力执行前调用 ensureSession，但不等于每次都强制打开页面实时 verify。

~~~text
ensureSession(shopRecordId, requiredOrigins, riskLevel)
  -> 读取每个 origin 当前状态
  -> 按 riskLevel 计算 TTL
  -> 缺失、过期或状态非 logged_in 时触发 verify
  -> 如果有登录窗口正在打开，返回 needs_manual_handoff
  -> 如果 captcha/two_factor/blocked，暂停该店 partition
  -> 高风险写操作提交前执行轻量 freshness check
~~~

TTL：

| 场景 | TTL |
|---|---|
| 只读商品预览 | 10 分钟 |
| 经营、资金、售中、违规采集 | 5 分钟 |
| 营销创建、删除、改价、删除商品 | 3 分钟 |
| 执行中遇到登录失效 | 立即 expired |
| 风控、验证码、2FA | 不使用 TTL |

### 8.6 人工接管

当任务分区进入 paused_manual_handoff：

- 只暂停对应 shopRecordId。
- 其他店铺继续执行。
- UI 任务中心显示“需人工接管”。
- 用户打开登录窗口处理后，点击“恢复该店任务”。
- 恢复前重新运行 ensureSession。

## 9. Profile HTTP 方案

### 9.1 设计目标

ProfileHttpService 在指定 Profile 的正确 origin 页面内发请求，复用浏览器凭据，不把 Cookie 持久化为业务状态。为保留下载和导出便利性，DownloadService 可在一次请求生命周期内临时读取当前 Profile 的 Cookie header。

首版不假设 Tianshe 提供 `profileFetch` 或独立 HTTP helper。ProfileHttpService 必须基于 `helpers.profile.withLease(profileId, options, callback)` 取得浏览器上下文后，在目标 origin 的页面内执行受控 `fetch` 或等价浏览器动作。具体执行方式由 Runtime 验证锁定，并写入 `runtime-validation-report.md`。

Gate 2 前必须完成 `profile-http-spike-report.md`，至少验证：

| 能力 | electron-webcontents | chromium-extension-relay | 验收 |
|---|---|---|---|
| 在 fxg origin 页面内执行同源 fetch | 必测 | 必测 | 自动携带浏览器凭据；普通业务请求不需要 Cookie 字符串 |
| POST JSON/form | 必测 | 必测 | 平台能收到正确 body 和 content-type |
| 读取 status、业务码和受限响应正文 | 必测 | 必测 | 能在 `maxResponseBytes` 内分类错误 |
| AbortController 超时 | 必测 | 必测 | 超时可中断并释放 lease |
| response_too_large | 必测 | 必测 | 超限截断，artifact 只保存 hash 和摘要 |
| 导航跳登录/验证码 | 必测 | 必测 | 返回 login_expired/captcha，不盲重试 |
| 同 Profile 并发 | 必测 | 必测 | 写请求串行，只读并发不破坏页面状态 |
| 下载/导出 Cookie 桥接 | 必测 | 必测 | 仅当前 Profile、当前请求使用，不返回 UI、不写库、不写日志 |

如果某 runtime 无法满足上述能力，不得作为真实写操作 runtime；只能用于登录、诊断或只读能力。

### 9.2 ProfileHttpSession

ShopWorker 获取一次 lease 后按 origin 创建 session。`ProfileHttpSession` 是 per-origin 会话，不允许一个 session 跨 `fxg`、`compass`、`buyin` 切换。

~~~ts
type ProfileHttpSession = {
  shopRecordId: string
  profileId: string
  runtimeId: string
  origin: string
  request(req: ProfileRequest): Promise<ProfileResponse>
  close(): Promise<void>
}
~~~

一个 ShopWorker 在一个任务片段内只获取一次 withLease，在 callback 内执行多个 ProfileRequest。

同一 Profile 的 origin 切换必须经过 ProfileHttpService 内部互斥队列。只读并发只允许同 origin、同页面稳定状态下执行；写请求、导航、登录检测和人工接管检测全部串行。

`withLease` callback 外不得持有页面、browser handle、request function 或任何可继续访问 Profile 的闭包。所有请求必须在 lease 生命周期内完成，异常路径必须关闭临时页面或恢复到稳定 origin。

### 9.3 ProfileRequest

~~~ts
type ProfileRequest = {
  endpointKey: string
  origin: "fxg" | "compass" | "buyin"
  url: string
  method: "GET" | "POST" | "PUT" | "DELETE"
  query?: Record<string, string | number | boolean>
  headers?: Record<string, string>
  body?: unknown
  bodyType?: "json" | "form" | "text" | "none"
  timeoutMs: number
  maxResponseBytes: number
  risk: "read" | "write"
}
~~~

### 9.4 运行边界

- URL 必须命中 endpoint registry。
- host 必须在内置规则或 Hotfix Lite JSON 的 allowlist 中。
- request.url 的 origin 必须和当前页面 origin 一致。
- 禁止从 UI 传入任意完整 URL 执行。
- fetch 使用 AbortController，HTTP 超时和 lease 等待超时分别记录。
- 响应正文超过 maxResponseBytes 时截断并分类为 response_too_large。
- DownloadService 的一次性 Cookie header 只允许在当前 Profile、当前 origin、当前请求内使用；不得返回 UI、不得持久化、不得写入 artifact 内容。
- evidence 只保存 endpointKey、status、业务码、耗时、traceId、hash 和脱敏摘要。
- 不记录 Cookie、Authorization、完整请求头、完整响应正文。
- request.headers 只允许 endpoint registry 显式声明的安全 header；禁止透传 UI 或平台原始 header。
- ProfileHttpService 返回值必须先经过 response-classifier 和 redactor，再进入 JobEngine、artifact 或 UI API。

### 9.5 响应分类

response-classifier 按 endpoint 级规则判断：

统一 ErrorCategory 枚举为：

~~~text
login_expired
captcha
permission
rate_limit
validation
business_conflict
platform_changed
network
unknown_result
unknown
~~~

| 分类 | 判断依据 | 处理 |
|---|---|---|
| login_expired | 跳登录页、明确登录业务码、session 失效 | 标记 origin expired，暂停该店 |
| captcha | 页面或接口提示滑块、验证码 | 标记 captcha，人工接管 |
| permission | 权限不足、功能未开通 | 不重试，提示用户 |
| rate_limit | 频繁、繁忙、限流 | 按能力策略退避 |
| validation | 参数非法、商品状态不符 | 不重试，写失败 |
| business_conflict | 活动冲突、价格限制、规则冲突 | 不重试，写失败 |
| platform_changed | 字段缺失、结构变化、未知 schema | 熔断该 endpoint，提示更新规则 |
| network | 网络超时、断网 | 可按策略重试 |
| unknown_result | 写请求发出后结果未知 | 进入对账状态 |
| unknown | 未分类异常 | 低次数重试后失败 |

## 10. 持久任务引擎

### 10.1 总体流程

~~~text
createPlan
  -> bounded dry run 生成预览，或 createPlanJob 异步生成预览
  -> confirmPlan 记录确认凭证
  -> submitJob 创建 job / partitions / items
  -> JobDispatcher 调度 partitions
  -> ShopWorker 持有 Profile lease
  -> ensureSession
  -> claim pending items
  -> 写 attempt
  -> 执行平台请求
  -> classify response
  -> 更新 item / partition / job
  -> artifact 导出
~~~

计划生成规则：

- `createPlan` 只允许执行 bounded preview，超出 capability 的 `maxSyncItems` 或 `maxSyncDurationMs` 时返回 `planJobRequired`。
- `createPlanJob(capability, input)` 创建异步计划任务，返回 `planJobId`。
- `getPlanJob(planJobId)` 返回计划生成进度；完成后写入 `xzb_operation_plans` 并返回 `planId`。
- `confirmPlan` 必须校验 plan 状态为 ready、previewHash 未变化、rulesVersion 和 rule_config_hash 未变化。

### 10.2 状态机

Job 状态：

~~~text
pending -> running
running -> succeeded
running -> partial_failed
running -> failed
running -> cancelling -> cancelled
running -> cancelling -> cancelled_with_effects
running -> interrupted
running -> needs_reconciliation
~~~

JobItem 状态：

~~~text
pending -> claimed -> running
running -> succeeded
running -> failed
running -> retry_wait -> pending
running -> skipped
running -> unknown_result -> needs_reconciliation
running -> interrupted
pending -> cancelled
claimed -> cancelled
~~~

### 10.3 Claim 规则

Worker 领取 item 必须使用条件更新：

~~~text
update xzb_job_items
set status = claimed,
    claimed_by = workerId,
    claimed_until = now + claimTtl
where id = itemId
  and status in (pending, retry_wait)
  and (next_retry_at is null or next_retry_at <= now)
~~~

更新影响行数为 1 才算领取成功。

### 10.4 并发和限流

| 项 | MVP 默认 |
|---|---|
| 多店并发 | 3 个 ShopWorker |
| 单店 lease | 同一 Profile 同时 1 个 worker |
| 单店请求并发 | 同 origin ProfileHttpSession 内最多 2 个只读请求；写请求、导航、登录检测串行 |
| 单请求超时 | 30 秒 |
| claim TTL | 2 分钟，长请求需 renew |
| rate limit 退避 | 30 秒、90 秒、180 秒 |
| 登录失效 | 不重试，暂停该店 |
| 写操作未知结果 | 不盲重试，先对账 |

### 10.5 重试策略

| 能力类型 | 重试策略 |
|---|---|
| 只读采集 | 网络、限流可重试 |
| 可幂等写 | 使用 idempotencyKey 或平台状态确认后重试 |
| 不可幂等创建 | 不盲重试，必须对账 |
| 删除/彻删 | 只允许在目标仍存在且状态匹配时重试 |
| 改价/改标题 | 写前校验 before 值，变化则跳过并要求重新预览 |
| 营销创建 | 使用业务唯一名或外部关联键对账后再决定 |

### 10.6 恢复流程

插件启动时：

~~~text
recoverInterruptedJobs()
  -> running/cancelling 且 heartbeat 过期的 job 标记 interrupted
  -> claimed/running 且 claimed_until 过期的 item 标记 interrupted
  -> 只读任务可自动恢复
  -> 可幂等写任务重新检查平台状态
  -> unknown_result 进入 needs_reconciliation
  -> 不可幂等任务要求人工确认
~~~

恢复不允许直接重复执行高风险写 item。

### 10.7 取消

取消是协作式：

- 未开始 item 置 cancelled。
- 已 claimed 但未发请求 item 可取消。
- in-flight 写请求不能强杀为失败，必须等待返回或进入 unknown_result。
- 已产生副作用的 job 取消后状态为 cancelled_with_effects。

### 10.8 汇总统计

job 的 total、success、failed、skipped、unknown 优先由 job_items 终态查询派生。缓存字段只做展示优化，不能作为唯一事实。

| Gate 4 | retryFailedItems(jobId, itemIds) | 重试可重试失败项 |
| Gate 3/4 | exportJobFailures(jobId, format) | 导出失败 |
| Gate 3/4 | getArtifacts(jobId) | 查询产物 |

API 暴露实现合同：

~~~ts
export async function activate(rawContext, rawHelpers) {
  const { context, helpers } = createTiansheCompatibilityAdapter(rawContext, rawHelpers)
  const services = await bootstrapXzbServices(helpers)

  context.exposeAPI(safeExposeAPI({
    getAppStatus: services.runtime.getAppStatus,
    listCapabilities: services.capability.listCapabilities,
    listShops: services.shop.listShops,
    createShopBinding: services.shop.createShopBinding,
    openLogin: services.login.openLogin,
    getLoginSession: services.login.getLoginSession,
    verifyLoginSession: services.login.verifyLoginSession,
    closeLoginSession: services.login.closeLoginSession
  }))
}
~~~

`context.exposeAPI()` 必须在 ActivityBar 页面首次加载前完成当前发布启用 API 的一次性注册。Tianshe 当前页面注入逻辑在页面加载时读取 exposed API 列表快照，后续动态新增 API 不会自动补注入。因此：

- `activate()` 中必须先完成 `bootstrapXzbServices()` 和当前 Gate API map 构造，再调用一次 `context.exposeAPI(safeExposeAPI(currentGateMap))`。
- 不允许在同一页面生命周期内按点击懒注册 API；未来 Gate 的 API 可以暂不暴露，UI 通过 `listCapabilities()` 和 `getAppStatus()` 判断可用能力。
- 如果为了前端兼容提前暴露未就绪 API，必须返回标准错误 `FEATURE_NOT_READY`，不得执行半成品逻辑。
- Contract test 必须校验当前 Gate 首屏所需 API 都出现在 `window.pluginAPI.xzb_toolbox`，Gate 0 不要求验证所有未来 API。
- 如未来确需动态 API，必须实现页面 reload 或重新注入机制，并单独更新本合同。

`safeExposeAPI()` 是必需边界，不是可选工具：

- 对所有已启用 API 的 args 做 runtime schema 校验和业务 guard。
- 对所有已启用 API 的 result 做 DTO 白名单序列化，禁止返回 browser handle、Profile 对象、Account 原始对象、完整 header、Cookie、Authorization、raw platform response。
- 捕获 Tianshe/helper/数据库/平台原始异常，统一转换为 `{ code, category, message, retryable, correlationId }`。
- 日志和 API 摘要只记录脱敏后的 DTO；数据库错误不得带出 SQL 或 params。
- 每个当前 Gate exposed API 必须有 contract test 覆盖成功、校验失败和内部异常归一；完整脱敏矩阵随 Profile HTTP、artifact 和 job Gate 补齐。

前端 ActivityBar 页面调用合同：

- 页面必须等待 `window` 的 `pluginAPIReady` 事件。
- 只接受 `event.detail.pluginId === "xzb_toolbox"` 的 API 注入。
- API client 从 `window.pluginAPI.xzb_toolbox` 创建。
- API args 和 result 必须是脱敏 DTO，不得包含 Cookie、Authorization、完整 header、完整响应正文、收件人敏感明文或 raw platform response。
- 所有 API 失败统一返回标准错误 DTO，UI 不解析 Tianshe 原始异常文本。
- UI 不得直接调用 `window.electronAPI.jsPlugin.callPluginAPI`；只能使用小尊宝 API client，便于统一超时、错误分类和脱敏。
- UI 不得从 `localStorage`、`sessionStorage`、`IndexedDB`、CacheStorage 恢复店铺、Profile、登录、确认凭证、job 或规则版本事实；这些状态必须通过 API 从小尊宝服务端状态层读取。
- UI 缓存只能保存视图偏好，例如列表列宽、筛选器草稿、折叠状态；插件激活、切换版本或检测到 schemaVersion 变化时必须可清空。

`crossPlugin.exposedAPIs` 与 `context.exposeAPI` 的区别：

| 项 | 作用 |
|---|---|
| crossPlugin.exposedAPIs | 跨插件或 MCP 授权声明，不注册运行时 API |
| context.exposeAPI | 插件页面实际可调用 API 的唯一注册入口 |
| mcpCallable | 只控制 MCP/HTTP 调用，不限制本机 ActivityBar 页面 |

- 预览页必须显示每店、每商品、修改前、修改后、跳过原因。
- 删除、彻删、营销创建、清理滞销执行需要二次确认。
- previewHash 变化时确认按钮失效，要求重新预览。
- 任务提交后立即返回 jobId，跳转任务中心。

## 15. 规则配置、Hotfix Lite 与版本固定

### 15.1 首版裁剪范围

首版不实现以下能力：

- 插件包自更新。
- update manifest 检查、下载、验签、staging 安装和回滚。
- 独立规则包下载、验签、激活、retire 和回滚。
- `xzb_rule_packages`、`xzb_update_history` 等热更新状态表。

插件包本身随安装包发布。规则配置首选内置随包发布，同时保留 Hotfix Lite JSON 作为平台接口变化后的便利修复通道。Hotfix Lite 不是完整规则包热更新，不允许远程可执行 JS，不引入插件自更新生命周期。

### 15.2 内置规则与 Hotfix Lite

内置规则配置包含：

- endpoint 映射。
- endpoint host allowlist。
- 错误码映射。
- 标题规则默认配置。
- 各能力的字段映射和响应 schema hash。

Hotfix Lite 可覆盖：

- endpoint path 模板和参数映射。
- 错误码、限流、登录失效、字段变更等响应分类规则。
- 字段映射和 response schema hash。

规则配置和 Hotfix Lite 均不得包含：

- 任意 JS 代码。
- 任意 host。
- 任意完整 URL。
- 绕过验证码、短信、2FA 或风控的逻辑。

`RuleConfigService` 在插件 activate 时加载内置规则配置，并校验：

- schemaVersion 合法。
- endpoint host 属于固定 allowlist。
- endpoint path 模板合法。
- `rulesVersion`、`endpointVersion` 和 `ruleConfigHash` 可计算。
- Hotfix Lite 下载失败、校验失败或版本不兼容时回退 last-known-good；没有 last-known-good 时回退内置规则。

### 15.3 运行时版本固定

`createPlan` 生成预览时必须记录当前 `rulesVersion`、`endpointVersion`、`ruleConfigHash` 和 `configSource`。`confirmPlan` 和 `submitJob` 必须校验这些值未变化。

`submitJob` 创建 job 时写入 `pluginVersion`、`rulesVersion`、`endpointVersion`、`ruleConfigHash` 和 `configSource`。执行 item 时只读取 job 绑定版本，运行中的 job 不受后续插件包升级、本地配置变化或 Hotfix Lite 更新影响。

## 16. 可观测性和脱敏

### 16.1 日志字段

每条结构化日志至少包含：

| 字段 | 说明 |
|---|---|
| pluginVersion | 插件版本 |
| jobId | 任务 ID |
| partitionId | 店铺分区 |
| itemId | 明细 |
| shopRecordId | 店铺记录 |
| capability | 能力 |
| endpointKey | endpoint |
| attemptNo | 尝试次数 |
| rulesVersion | 规则版本 |
| durationMs | 耗时 |
| errorCode | 标准错误 |

### 16.2 脱敏规则

禁止进入日志、evidence、artifact、UI API args/result、Tianshe observation span：

- Cookie。
- Authorization。
- token、csrf、session、passport 类字段。
- 完整请求头。
- 完整响应正文。
- 默认完整收件人姓名、电话、地址。

允许进入 evidence：

- URL origin 和 endpointKey。
- HTTP status。
- 业务 code。
- trace id。
- 响应 schema hash。
- 脱敏字段摘要。

Tianshe 会对插件 API 的 args/result 做运行时摘要记录。小尊宝不能依赖 Tianshe 摘要器做业务脱敏；所有已暴露 API 的入参和返回值在进入 `context.exposeAPI` 边界前就必须是安全 DTO。

契约测试按 Gate 覆盖：

- Gate 0 覆盖已启用 API 的 DTO 白名单和数据库错误归一。
- Gate 2 覆盖 ProfileHttpService evidence，不含 raw header、raw response 和个人敏感明文。
- Gate 3/4 覆盖 job、artifact、failure export 和 observation payload 摘要，不出现 token、cookie、session、authorization、phone、address 等字段和值模式。

### 16.3 Artifact

| 类型 | 生成时机 |
|---|---|
| failure_export | 用户导出失败列表 |
| diagnostic_bundle | 用户发起诊断 |
| screenshot | 登录或页面状态无法判断 |
| download | 罗盘或平台导出 |

## 17. 运行边界与便利通道

### 17.1 API 与跨插件边界

MVP：

- mcpCallable 为 false。
- allowedCallers 为空数组。
- 不暴露 submitJob 给跨插件或 MCP；跨插件/HTTP 写操作不是首版目标。
- 只读状态 API 可在后续显式开放，但不得绕过当前 Gate API 合同。
- 本机 ActivityBar 页面可调用当前 Gate `context.exposeAPI` 注册的 API，因此写型 API 必须检查 plan、Runtime 写验证和 job 幂等状态，不能只依赖 crossPlugin 配置。

### 17.2 Plan 确认和幂等提交

确认凭证：

- 由本机 UI confirmPlan 签发或记录确认上下文。
- 绑定 planId、capability、inputHash、previewHash、shopRecordIds、ruleConfigHash、rulesVersion、endpointVersion、expiresAt。
- 保存 hash，不保存明文。
- 默认 30 分钟过期，或不超过 plan 的 `expires_at`。
- submitJob 后立即失效。
- localUserSession hash 可作为增强字段，但不作为首个闭环硬阻断。

`submitJob` 必须以等价原子逻辑消费 confirmed plan：

~~~text
begin logical transaction
  read plan where id = planId
  assert status = confirmed
  assert preview_hash = request.previewHash
  assert input_hash = request.inputHash
  assert confirm_token_expires_at > now
  assert rule_config_hash and rulesVersion still match plan
  assert runtimeWriteStatus = passed for write capability
  insert xzb_jobs / partitions / items
  update xzb_operation_plans
    set status = submitted,
        confirm_token_hash = null,
        confirm_session_hash = null,
        confirm_token_expires_at = null,
        updated_at = now
    where id = planId
      and status = confirmed
commit
~~~

如果 DuckDB helper 无法提供显式事务，Service 层必须使用条件更新、唯一键和幂等 job 创建键保证重复提交只会产生一个 job。

### 17.3 URL、Hotfix 和 Cookie 桥接边界

内置规则和 Hotfix Lite 配置只允许以下平台 host 族作为业务请求目标：

| Origin | Host |
|---|---|
| fxg | fxg.jinritemai.com |
| compass | compass.jinritemai.com |
| buyin | buyin.jinritemai.com |

如果确实需要 exportProxyUrl，必须：

- 进入产品和稳定性评审。
- 使用固定配置和本地兜底。
- 限定固定 host。
- 不作为通用 HTTP 代理。
- 只传递用户已下载文件、短期临时授权或当前请求所需的一次性 Cookie header。
- 一次性 Cookie header 不写库、不进日志、不返回 UI，不跨 Profile/Runtime 复用。

## 18. 测试和验收

### 18.1 阶段 0 验收

- Tianshe commit 锁定。
- `runtime.default` 是显式合法值，默认 `electron-webcontents`；adapter 不会把空 runtimeId 传给 Tianshe。
- Electron 登录/只读 Runtime 验证完成并记录结果；写能力验证状态可以是 pending。
- helpers adapter 契约测试通过。
- migration runner 可创建、升级、重复执行。
- manifest 可安装，ActivityBarView 可打开。
- manifest validator 拒绝 remote executable ActivityBar source、越界 source.path、空 runtime.default 透传。
- `context.exposeAPI` 注册表和 UI API client 契约测试通过。
- `pluginAPIReady` 后页面可调用 Gate 0 首屏 API 集合，包括 `getAppStatus()`、`listShops()`、`createShopBinding()`、`openLogin()`。
- 写能力验证 pending/failed 时真实写操作入口关闭，但不阻断新建店铺、人工登录和只读验证。
- adapter 契约测试证明无法通过 `profile.update` 原地修改 Profile Runtime。
- Gate 0 exposed API DTO 白名单和数据库错误归一测试通过。
- 最小 xzb_ 表可读写，核心 JSON 字段向后兼容测试通过。

### 18.2 登录验收

- 打开登录窗口后点击检测不会卡住。
- 检测按钮 3 秒内有状态反馈，验证复用当前 popup browser。
- 关闭窗口、插件 reload、应用退出都能释放 handle。
- 重启 Tianshe 后登录态仍在 Profile 内。
- fxg origin 状态必须记录；compass、buyin 可在对应功能 Gate 前补齐。
- 验证码、短信、2FA、blocked 返回人工接管。
- 重复 shopId 能识别并阻止任务执行。

### 18.3 任务验收

- submitJob 立即返回 jobId。
- 大样本 createPlan 可在 Gate 3 后半段或 Gate 5 走 createPlanJob，不阻塞 UI API 超时预算。
- 副作用前 job、partition、item、attempt 已落库。
- 单店失败不影响其他店。
- 单商品失败不影响其他商品。
- 取消任务后未开始项不会执行。
- 崩溃重启后 running 任务不永久悬挂。
- unknown_result 不盲重试。
- 失败列表 Gate 3 必须可导出 CSV；Excel 可在 P1 扩展期补齐。

### 18.4 商品批量验收

- 批量改标题有规则测试向量。
- 批量改价按 SKU 预览和执行。
- 批量删除有在售保护和 typed confirm。
- 批量上下架过滤已处于目标状态商品。
- 达人秀开启和关闭都有预览。
- 运费模板复制和商品绑定分开验收。

### 18.5 数据采集验收

- 多接口部分失败时其他指标继续。
- 导出包含店铺、采集时间、字段来源、失败原因。
- compass 未激活时只影响相关指标。
- 售中敏感字段默认脱敏。

### 18.6 故障注入

必须覆盖：

- 断网。
- 平台 401、403、限流、繁忙。
- 页面跳登录。
- 验证码和短信。
- 应用强制退出。
- 磁盘不足。
- migration 中断。
- 写请求返回前断开。

## 20. 风险和应对

| 风险 | 应对 |
|---|---|
| Electron 被平台识别或写能力不稳定 | 登录/只读先用 Electron；写能力验证失败时新 Profile 使用 Extension |
| 平台接口字段变化 | endpoint registry、内置规则 schema 校验、Hotfix Lite JSON、platform_changed 熔断 |
| 登录频繁失效 | origin 级 TTL、写前 freshness check、人工接管 |
| 任务崩溃重复写 | idempotencyKey、attempt、unknown_result、对账 |
| 大店分页过多 | 创建时间分段、限流、分批 checkpoint |
| 营销创建重复 | 业务唯一名、创建后查询、不可幂等不盲重试 |
| 删除误操作 | typed confirm、在售保护、预览、写前校验 |
| 临时 Cookie 桥接失控 | 只允许当前 Profile/当前请求内使用，不写库、不入日志、不返回 UI |
| 敏感数据进入产物 | 字段白名单、默认脱敏、artifact hash 和保留周期 |
| Tianshe API 调整 | 版本锁定、adapter 层、契约测试 |

## 21. 待确认问题

以下问题不阻塞 Gate 0，但必须在对应功能开发前确认：

1. 店铺管理是否必须包含订购状态和功能包状态。
2. 店铺删除时是否默认保留 Profile 凭据。
3. 售中管理是否需要采集完整收件信息。
4. 自动续期和自动提报是否进入首版 P3。
5. 清理滞销的罗盘数据是否可直接下载，是否需要 exportProxyUrl。
6. 内置规则和 Hotfix Lite 配置由谁评审、发布和回滚。
7. 高风险操作是否需要额外业务审批。
8. 是否允许按客户环境差异化内置规则配置。

## 22. 最终建议

小尊宝稳定版的核心不是照搬旧小尊宝的远程 Web、热更新插件和 Cookie 长期搬运，而是把便利能力收束到稳定可恢复的本地产品架构：

~~~text
Profile 管凭据
LoginSessionController 管人工登录窗口
OriginSession 管登录健康事实
ProfileHttpSession 管同 Profile 请求
DownloadService 管一次性下载/Cookie 桥接
Capability 管产品能力合同
OperationPlan 管预览和确认
JobEngine 管持久任务和恢复
Site Adapter 管平台页面和字段变化
Artifact 管导出和证据
RuleConfigService 管内置规则、Hotfix Lite、版本固定和 endpoint allowlist
~~~

开发顺序必须先稳登录、状态库、Profile HTTP/下载便利、任务恢复和首个写功能，再扩展 16 个功能。只要这个底座成立，后续功能是能力规格和 endpoint 适配的扩展；如果跳过这些底座直接堆功能，稳定性会重新回到旧架构的问题里。

首版只允许通过 `compatibility-adapter.ts` 调用以下 helper，不在业务代码中散落直接调用。

| helper | 首版用途 | 约束 |
|---|---|---|
| `helpers.profile.create` | 新建店铺 Profile | 必须传显式 runtimeId；Gate 0 可使用 `electron-webcontents` 登录/只读；空值或未知值时 adapter 必须拒绝调用 |
| `helpers.profile.update` | Tianshe 原始 helper 支持更新 Profile | 首版不透传；禁止用它修改 runtimeId、fingerprintSource、runtimeSourceOverride |
| `helpers.profile.launchPopup` | 打开人工登录窗口 | LoginSessionController 统一持有和释放 |

| `helpers.savedSite.create / ensureDoudianSavedSite` | 绑定抖店 SavedSite | 新店铺 Saga 内执行 |

| `helpers.database.executeSQL` | `xzb_` 表 migration 和查询 | 只能由 `XzbDatabaseRepository` 调用；migration 不传 datasetId；捕获错误后必须移除 SQL 和 params |
