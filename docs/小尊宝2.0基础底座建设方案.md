# 猎狐（小尊宝 2.0）基础底座建设方案

> 日期：2026-07-02  
> 版本名称：猎狐（小尊宝 2.0）  
> 目标：基于小尊宝工具箱 V2.1.6 的既有 Electron 本地能力层，建设一个可灰度、可回退、可持续扩展的自建远程 Web 底座。  
> 核心结论：用户不更新客户端。现有客户端仍从 `OLD_REMOTE_ENTRY` 进入，但该远程入口由我们重新建设并引导到新的远程 Web。新远程 Web 不复用旧站 Web Cookie、localStorage 或 IndexedDB；旧远程 Web 源码不可用，只基于线上产物和行为复刻。

## 1. 结论

猎狐第一阶段采用：

```text
现有 Electron 本地能力层不重构
  + OLD_REMOTE_ENTRY 远程入口重新建设
  + NEW_REMOTE_WEB_ORIGIN 自建新远程 Web
  + Legacy App Replica 复刻旧远程主站能力
  + Liehu Shell 灰度承载新界面和新功能
  + liehuBridge 统一适配 window.client
  + liehu20_ 作为新增数据默认命名规范
```

第一阶段不是重做客户端，也不是要求用户安装新包；它的重点是把原来由 `https://apptool.zzbtool.com` 承载的远程 Web 能力迁移到我们可控的新远程 Web 体系中。

第一阶段必须坚持三条红线：

1. Electron 本地能力层不重构：`window.client`、`persist:myappzzbtool`、preload、Cookie/session、DB、窗口、下载、日志和远程插件底层能力保持兼容。
2. 旧远程主站只作为复刻样本和兼容基线：不依赖旧源码，不把旧站继续作为目标运行主站。
3. 旧功能、旧登录能力、旧插件入口和旧数据结构继续可用。

## 2. 术语和占位符

| 名称 | 含义 |
|---|---|
| `OLD_REMOTE_ENTRY` | 现有客户端默认加载的远程入口，当前为 `https://apptool.zzbtool.com`。Phase 1 用户不更新客户端，因此这个入口必须由我们重新建设或接管。 |
| `NEW_REMOTE_WEB_ORIGIN` | 新远程 Web 的目标 origin。文档中的 `https://www.liehu.com` 只是占位符，不代表最终正式域名。 |
| 旧线上主站 | 原 `https://apptool.zzbtool.com` 的线上表现、资源、路由、交互和接口行为。 |
| Legacy App Replica | 在自建新远程 Web 中复刻旧线上主站能力的旧功能承载层。 |
| Liehu Shell | 猎狐新版 Shell，包含新版首页、布局、导航、状态栏、诊断入口和旧页面容器。 |
| Electron 本地能力层 | 现有 Electron 主进程、preload、`window.client`、partition、DB、窗口、下载、日志等本地能力。 |
| `liehuBridge` | 猎狐新代码访问 `window.client` 的统一桥接层。 |
| `liehu20_` | 猎狐新增数据的默认命名规范，不是 DB 能力拦截规则。 |

## 3. 当前事实基线

从现有生产包和分析材料看，小尊宝 V2.1.6 当前底座是：

- Electron 主窗口加载 `OLD_REMOTE_ENTRY`，当前值为 `https://apptool.zzbtool.com`。
- 主窗口 session partition 是 `persist:myappzzbtool`。
- preload 是 `dist-electron/main/preload/index.js`。
- 远程 Vue 主站通过 `window.client` 调用本地 Cookie、HTTP、窗口、DB、下载和日志能力。
- `work-server/http.js` 会把响应 `Set-Cookie` 回写指定 partition。
- 远程插件通过 `v3config` 下载 `v3_all.js`、CSS 和 popup 页面。
- 现有业务围绕店铺、平台 Cookie、隐藏窗口、DB 和远程插件形成事实闭环。

第一阶段正确策略是替换远程 Web 主站，而不是重构本地能力层。

## 4. 第一阶段边界

| 项目 | 当前小尊宝 V2.1.6 | 猎狐 Phase 1 | 要求 |
|---|---|---|---|
| 客户端更新 | 用户使用现有客户端 | 用户不更新客户端 | 不发 Electron 客户端包 |
| 远程入口 | `OLD_REMOTE_ENTRY` | 重新建设远程入口，远程引导到 `NEW_REMOTE_WEB_ORIGIN` 或直接承载新站 | 由服务端/远程入口完成切换 |
| 新远程 Web | 无 | `NEW_REMOTE_WEB_ORIGIN`，示例占位为 `https://www.liehu.com` | 自建、可灰度、可回退 |
| 旧站能力 | 原线上主站 | Legacy App Replica | 基于线上产物和行为复刻 |
| 主窗口 partition | `persist:myappzzbtool` | 不改 | 完全兼容 |
| preload | 现有 preload | 不改 | 完全兼容 |
| `window.client` | 现有方法继续暴露 | 不删不改 | 完全兼容 |
| Cookie / session | 现有本地读写和回写链路 | 不改本地能力 | 不等同于复用旧 Web 存储 |
| HTTP 通道 | `window.client.http` | `HttpBridge` 包装，兼容旧 `axiosParmars` 拼写 | 不假设自动带 Cookie |
| 隐藏窗口 | `openWindow`、`editBrowserWindow`、`executeJavaScriptBrowserWindow` 等 | `WindowBridge` 保留 raw URL / raw JS 能力 | 不做治理拦截 |
| 本地 DB | `db` / `_db` | `DbBridge` 保留旧库、旧表、旧命令能力 | 不因 `liehu20_` 收窄 |
| 远程插件 | `v3_all.js` 热更新机制 | 不改插件发布链路 | 处理入口跳转兼容 |

第一阶段不做：

- Electron 本地能力层重构。
- 新 preload API。
- 新登录系统。
- 新浏览器 Profile 系统。
- 新插件平台。
- 旧功能全量重写。
- 应用标题、图标、安装包名称变更。
- raw JS、raw URL、危险 DB 命令治理；这些能力作为兼容合同保留，后续也不作为强制治理任务。

## 6. 远程入口和新主站策略

### 6.1 用户不更新客户端

现有客户端仍加载 `OLD_REMOTE_ENTRY`。为了让用户不更新客户端也进入新远程 Web，`OLD_REMOTE_ENTRY` 必须由我们重新建设为远程入口层：

1. 优先加载入口配置。
2. 判断是否进入 `NEW_REMOTE_WEB_ORIGIN`。
3. 可通过 redirect、HTML bootstrap 或远程 loader 进入新远程 Web。
4. 新远程 Web 不可用时，入口层必须能回到 Legacy App Replica 或硬兜底页。

因此 Phase 1 不发布 Electron 客户端包，也不依赖用户更新客户端。

### 6.2 新远程 Web 域名

`https://www.liehu.com` 只是 `NEW_REMOTE_WEB_ORIGIN` 的文档占位符。正式方案中所有环境都应使用变量：

| 环境 | 变量 |
|---|---|
| 测试 | `NEW_REMOTE_WEB_ORIGIN_TEST` |
| 预发 | `NEW_REMOTE_WEB_ORIGIN_STAGING` |
| 生产 | `NEW_REMOTE_WEB_ORIGIN_PROD` |
| 回滚 | `REMOTE_ENTRY_FALLBACK_ORIGIN` |

主文不再硬编码正式域名，避免占位符进入发布配置。

### 6.3 旧站复刻方式

旧远程 Web 源码不可用。Legacy App Replica 只能基于以下材料重建：

- 线上 HTML、JS、CSS、图片、字体和动态 chunk 产物。
- 线上路由、菜单、按钮入口和插件入口行为。
- 网络请求、接口参数、响应结构和错误表现。
- 页面状态、跳转、弹窗、下载、隐藏窗口和平台注入行为。
- 已有分析材料、抓包结果和生产包审计结论。

不得假设可以拿到旧主站源码、构建命令或内部组件结构。Phase 0 的任务是产出复刻清单，而不是寻找旧源码作为前提。

### 6.4 新主站不复用旧 Web 存储

新远程 Web 不迁移、不读取、不复用旧站的 Web Cookie、localStorage 或 IndexedDB。

这意味着：

- `persist:myappzzbtool` 只保证 Electron session partition 不变，不保证跨 origin 的 Web 存储可读。
- 新主站建立自己的 Web 存储命名和缓存策略。
- 旧功能需要的登录、店铺、平台态信息优先通过 `window.client`、接口、平台 Cookie、本地 DB 或重新拉取获得。
- 不把旧站 localStorage / IndexedDB 作为灰度判断、登录判断或业务状态事实源。
- 如果旧线上主站某个功能依赖 Web 存储，必须在 `legacy-site-rebuild-map.md` 中记录，并为 Legacy App Replica 重新实现等价状态来源。

### 6.5 接口和 Origin 兼容

换到 `NEW_REMOTE_WEB_ORIGIN` 后，不能默认浏览器请求仍然可用。必须梳理：

- CORS 允许的 Origin。
- Referer / Origin 校验。
- Cookie Domain 和 SameSite。
- 重定向目标。
- 静态资源绝对路径。
- 接口域名白名单。
- 是否需要通过 `window.client.http` 代理或显式补 Header/Cookie。

所有接口必须进入 `legacy-site-rebuild-map.md` 或 `remote-web-release-map.md` 的兼容矩阵。

### 6.6 远程插件入口兼容

Phase 1 不改远程插件发布链路，但必须处理插件到主站的跳转入口。

处理原则：

- Phase 0 必须确认插件是否写死主站 URL。
- 如果插件写死 `OLD_REMOTE_ENTRY`，由 `OLD_REMOTE_ENTRY` 入口层接入新远程 Web，不要求立刻改插件代码。
- 如果插件 URL 来自远程配置，优先通过配置切到新入口或新 origin。
- popup、平台注入按钮、主站跳转和回退行为必须写入 `plugin-compatibility-matrix.md`。

### 6.7 启动流程

推荐启动流程：

```text
Electron 加载 OLD_REMOTE_ENTRY
  -> OLD_REMOTE_ENTRY 加载入口配置
  -> 入口配置命中新远程 Web
  -> 跳转或 bootstrap 到 NEW_REMOTE_WEB_ORIGIN
  -> 新远程 Web 启动
  -> 检测 window.client 是否存在
  -> 读取内置默认配置
  -> 读取 last-known-good 配置
  -> 拉取远程猎狐配置
  -> 通过 getAppInfo / 业务接口 / 本地 DB / window.client 能力获取灰度身份
  -> 命中灰度：进入 Liehu Shell
  -> 未命中或失败：进入 Legacy App Replica
```

`getClientVersionData` 只做异步诊断，不作为首屏和灰度判断的阻塞依赖。客户端版本优先读取 `getAppInfo().version`。

### 6.8 回滚和兜底

必须区分四类回退：

| 类型 | 触发场景 | 回退目标 |
|---|---|---|
| 入口级回退 | `NEW_REMOTE_WEB_ORIGIN` DNS、CDN、HTML 入口不可用 | `OLD_REMOTE_ENTRY` 硬兜底页或 Legacy App Replica |
| 配置级回退 | 远程配置不可用或配置校验失败 | last-known-good 配置；无缓存则默认 Legacy App Replica |
| Shell 级回退 | Liehu Shell 资源加载失败或运行错误 | Legacy App Replica |
| 数据级回退 | 猎狐新增数据初始化失败 | 禁用相关猎狐功能，保留旧功能 |

入口级回退不能依赖新主站 JS 执行。`OLD_REMOTE_ENTRY` 必须具备硬兜底能力。

## 7. 远程配置

远程配置只控制新远程 Web 内部行为，不改变 Electron 本地能力合同。

核心字段建议：

| 字段 | 说明 |
|---|---|
| `version` | 配置版本 |
| `shellMode` | `legacy` / `liehu` / `hybrid` |
| `configTtlSeconds` | 配置缓存时间 |
| `rollout` | 用户、店铺、版本、百分比、白名单、黑名单 |
| `routes` | 单路由进入 Legacy App Replica 或 Liehu Native |
| `features` | 单功能开关 |
| `assets` | Shell 资源入口和版本 |
| `endpoints` | 接口、资源和诊断端点 |
| `release` | commit、构建时间、manifest、回滚版本 |

必须支持的开关：

| 开关 | 用途 |
|---|---|
| `entry.newRemote.enabled` | `OLD_REMOTE_ENTRY` 是否引导到新远程 Web |
| `shell.liehu.enabled` | 是否启用 Liehu Shell |
| `shell.legacyReplica.enabled` | 是否允许进入 Legacy App Replica |
| `route.*.mode` | 单路由使用旧站复刻、新版页面或隐藏 |
| `feature.*.enabled` | 单功能开关 |
| `diagnostics.enabled` | 诊断采集开关 |
| `remotePlugin.entry.enabled` | 插件入口开关，默认不改变插件发布链路 |

## 8. `liehuBridge` 设计

猎狐新代码不得直接散落调用 `window.client`，必须通过 `liehuBridge`。

| Bridge | 包装现有能力 | 职责 |
|---|---|---|
| `AppBridge` | `getAppInfo`、`getClientVersionData`、`getMainWindowInfo` | 环境、版本、窗口信息；`getClientVersionData` 只做诊断 |
| `SessionBridge` | `get_cookies`、`set_cookies`、`copy_cookies`、`clear_session` | 保留 Cookie 读写、复制、清理能力；辅助生成目标 URL Header |
| `HttpBridge` | `http` | 兼容旧 `axiosParmars` 拼写、旧参数和旧返回；需要登录态时显式合并 Header/Cookie |
| `WindowBridge` | `openWindow`、`editBrowserWindow`、`executeJavaScriptBrowserWindow`、`reloadHomeUrl` | 保留 raw URL、raw 窗口编辑、raw JS 执行和主窗口重载 |
| `DbBridge` | `db`、`_db` | 保留旧库名、旧表名、旧命令、旧参数和旧返回，包括 `selfSql`、`resetDatabase`、`batchDelete` |
| `FileBridge` | 下载、保存、打开目录 | 文件导出和落盘 |
| `LogBridge` | `reportClientLog`、crash log API | 保留旧日志上报透传；猎狐新增诊断日志默认脱敏 |

`axiosParmars` 是旧接口真实拼写，兼容时不得擅自改成 `axiosParams`。

`liehuBridge` 保护规则：

- 检测 `window.client` 是否存在。
- 给每个调用生成 `correlationId`。
- 统一错误格式，但不吞掉原始错误。
- 不打印 Cookie、Authorization、token、Set-Cookie、完整请求头或完整响应体。
- 不删除、不隐藏、不阻断任何现有 `window.client` 方法。
- 不把“禁用任意 JS”“禁用任意 URL”“禁用危险 DB 命令”作为 Phase 1 或后续强制治理任务。
- 场景模板、审计字段和调用归属只做记录，不影响 raw 能力。

## 9. 数据和日志策略

猎狐新增数据采用“只增不改”策略。

`liehu20_` 是新增数据默认命名规范，不是 DB 能力拦截规则：

- 新增数据的 `dbName`、`tableName`、`recordType` 默认匹配 `liehu20_[a-z0-9_]+`。
- 新增数据命名避免路径分隔符、点号、空格、引号、分号和 SQL 关键拼接片段。
- 新增数据默认不依赖 `selfSql`、`resetDatabase`、`batchDelete`。
- 所有写入带 schema version 和调用来源。
- 新增数据初始化失败只禁用相关猎狐功能，不影响旧功能。

`DbBridge` 仍完整保留旧 `window.client.db` / `window.client._db` 的真实能力，不拦截旧库名、旧表名或旧命令。

建议新增数据表：

| 名称 | 用途 |
|---|---|
| `liehu20_meta` | schema/version/初始化状态 |
| `liehu20_preferences` | UI 偏好 |
| `liehu20_feature_state` | 功能开关本地状态 |
| `liehu20_recent_actions` | 最近访问、最近店铺 |
| `liehu20_diagnostics` | 诊断摘要 |
| `liehu20_config_cache` | last-known-good 配置 |

日志策略：

- 旧 `reportClientLog` 透传能力保留。
- 猎狐新增日志默认脱敏。
- 诊断包不得包含 Cookie、token、Authorization、完整请求头或完整响应体。

## 11. 发布和诊断底座

发布形态：

| 发布物 | 说明 |
|---|---|
| `OLD_REMOTE_ENTRY` | 重新建设的旧入口，负责无客户端更新进入新远程 Web 和硬兜底 |
| `NEW_REMOTE_WEB_ORIGIN` | 自建新远程 Web |
| Legacy App Replica | 旧站复刻层，可灰度、可回退 |
| Liehu Shell | 新版 Shell，远程发布 |
| Liehu Config | 独立配置，可热修、可回滚 |
| Remote Plugin Entry | 插件发布链路不改，入口跳转纳入兼容矩阵 |

灰度维度至少支持：

- 用户账号。
- 店铺 ID。
- 客户端版本。
- 渠道或环境。
- 百分比。
- 白名单。
- 黑名单。

诊断信息包括：

- 客户端版本。
- Electron / Chrome / Node 版本。
- 当前入口 origin。
- 当前 shell 模式。
- 远程配置版本。
- 当前路由。
- `window.client` 可用性。
- 最近 Bridge 错误。
- 最近页面加载错误。
- 是否触发入口级、配置级、Shell 级或数据级回退。

## 12. 实施路线

### Phase 0：线上基线和复刻清单

目标：确认旧线上主站、Electron 本地能力层、远程插件和旧功能路由的事实基线，并确定新远程 Web 的复刻范围。

任务：

- 基于旧线上主站产物和行为梳理复刻范围，不以旧源码可得为前提。
- 梳理旧版全量路由、菜单、按钮入口、插件入口和平台注入入口。
- 梳理旧站 HTML、JS、CSS、图片、字体、动态 chunk 和静态资源路径。
- 梳理旧站接口、请求头、响应结构、错误表现、CORS、Referer、Origin 和 Cookie 策略。
- 确认 `window.client` API 合同。
- 确认远程插件是否写死主站 URL。
- 确认用户、店铺和灰度身份来源。
- 确认入口级、配置级、Shell 级、数据级回退方案。

交付：

### Phase 1：新远程 Web 替换旧远程主站

目标：用户不更新客户端，通过重新建设的 `OLD_REMOTE_ENTRY` 进入自建新远程 Web，跑通 Legacy App Replica、Liehu Shell、配置、灰度、回退和诊断。

内容：

- 重新建设 `OLD_REMOTE_ENTRY` 入口层。
- 建设 `NEW_REMOTE_WEB_ORIGIN` 自建新远程 Web。
- 基于线上产物和行为建设 Legacy App Replica。
- 新建 Liehu Shell。
- 新建 `liehuBridge`。
- 新建配置加载器和 last-known-good 缓存。
- 新建入口级、配置级、Shell 级、数据级回退。
- 新建状态栏和诊断入口。
- 保留旧版全量路由、全量入口和远程插件入口。

验收：

- 用户不更新 Electron 客户端。
- 现有客户端加载 `OLD_REMOTE_ENTRY` 后能进入新远程 Web。
- `https://www.liehu.com` 只作为 `NEW_REMOTE_WEB_ORIGIN` 占位符，不写死为正式域名。
- 新主站不复用旧站 Web Cookie、localStorage 或 IndexedDB。
- 主 partition 仍是 `persist:myappzzbtool`。
- `window.client` 旧合同不破。
- Legacy App Replica 在验收清单覆盖范围内与旧线上主站行为一致。
- 新首页可按白名单或百分比灰度打开。
- 关闭配置后进入 Legacy App Replica。
- 新远程 Web 入口不可用时，`OLD_REMOTE_ENTRY` 有硬兜底。
- 不影响登录能力、远程插件、本地 DB、隐藏窗口和下载能力。
- `liehuBridge` 完整保留旧 `window.client` 方法、参数、返回和错误语义。
- `DbBridge` 完整保留 `selfSql`、`resetDatabase`、`batchDelete` 等旧命令。
- `WindowBridge` 完整保留 raw URL、raw JS、raw 窗口编辑和 `reloadHomeUrl`。
- `SessionBridge` 保留 Cookie 读写、复制、清理能力。
- `LogBridge` 保留旧 `reportClientLog` 透传能力。

## 13. 关键技术决策

### 决策 1：用户不更新客户端

理由：

- 当前客户端已经固定加载 `OLD_REMOTE_ENTRY`。
- 通过重新建设远程入口可以把用户引导到新远程 Web。
- 不把 Electron 包发布风险和远程 Web 改造风险叠在一起。

### 决策 2：替换远程 Web 主站，不重构本地能力层

理由：

- 当前登录、Cookie、HTTP、隐藏窗口、DB、下载和远程插件已经形成事实闭环。
- 重构本地能力层会把登录风险、会话风险和新 UI 风险叠加。
- 保留本地能力层，新增远程 Web 才有稳定承载面。

### 决策 3：旧站只做复刻基线

理由：

- 旧远程 Web 源码不可用。
- 只能基于线上产物和行为复刻。
- 新远程 Web 必须拥有独立源码、构建、发布、灰度和回滚能力。

### 决策 4：不复用旧 Web 存储

理由：

- 换 origin 后旧 Web Cookie、localStorage 和 IndexedDB 不可靠。
- 旧 Web 存储不应作为新主站登录、灰度或业务状态事实源。
- 新主站应建立自己的状态和缓存体系。

### 决策 5：保留主窗口 partition

理由：

- `persist:myappzzbtool` 是当前本地登录能力和平台 Cookie 能力的事实源之一。
- 改它会导致用户状态不可预测。

### 决策 6：新代码经过 `liehuBridge`

理由：

- 避免直接散落调用 `window.client`。
- 统一错误、日志、脱敏和降级。
- 保留旧能力的同时，为新功能提供稳定调用面。

### 决策 7：raw 能力永久兼容

理由：

- raw JS、raw URL 和危险 DB 命令是旧功能事实能力的一部分。
- Phase 1 不拦截，后续也不把它们作为强制治理任务。
- 如需审计，只记录调用归属，不改变可调用范围。

## 14. 最终建议

猎狐版第一步是把远程 Web 承载层拿回到我们可控的体系里：

1. 重新建设 `OLD_REMOTE_ENTRY`，让用户不更新客户端也能进入新远程 Web。
2. 建设 `NEW_REMOTE_WEB_ORIGIN` 自建新远程 Web。
3. 基于线上产物和行为复刻 Legacy App Replica。
4. 建设 Liehu Shell、配置、灰度、回退和诊断。
5. 通过 `liehuBridge` 兼容现有 `window.client`。
6. 新增数据使用 `liehu20_` 命名规范，不收窄旧 DB 能力。
7. 让旧页面、旧登录能力、旧插件和旧数据继续可用。

这套底座做好后，猎狐版才会从“一次 UI 改版”变成“可持续迭代的新版本平台”。
