# 小尊宝稳定版产品设计与技术实施方案：稳定性与便利性源码审计报告

> 审计对象：`docs/小尊宝稳定版产品设计与技术实施方案.md`  
> 对象版本：v2.2 Gate 0 阻断修订版  
> 审计主题：以稳定性和便利性为优先目标，重新判断方案中的硬约束、Gate 切分和实现顺序  
> 审计日期：2026-06-29  
> 源码对照：Tianshe `D:\code\tooltemp\tianshe\tianshe\src`，旧小尊宝解包产物 `D:\code\xiaozuibao\analysis_unpack`、`D:\code\xiaozuibao\analysis_output`

## 1. 总体结论

当前 v2.2 方案的底层方向是正确的：它试图用 Tianshe Profile、固定 Runtime、持久任务、失败隔离和恢复机制，替代旧小尊宝依赖远程 Web、热更新插件、Cookie 搬运和临时本地任务状态的做法。这些设计确实直接服务稳定性。

但如果本轮优先级是“稳定性和便利性，而不是安全性”，方案需要重新排序。当前文档把不少安全型约束前置成 Gate 0 阻断项，例如远程 UI 禁止、规则热更新禁止、完整 API 合同、完整脱敏扫描、ConfirmToken 本机会话绑定、MCP/跨插件限制等。这些约束不一定错误，但很多并不直接提升首个闭环的稳定性，反而会拖慢上线、增加开发摩擦、降低平台变更时的修复便利性。

建议把方案从：

```text
安全边界优先的稳定平台蓝图
```

修订为：

```text
先让店铺登录、只读验证、批量改标题和失败恢复稳定可用，再逐步补齐安全边界和平台化能力
```

一句话判断：

```text
稳定性底座必须保留，安全化硬门槛要降级；便利通道不能照旧裸奔，但应以本地兜底、缓存、回滚和版本固定来管理，而不是简单禁止。
```

## 2. 审计原则

本次审计不以“是否足够安全”为主轴，而以以下问题判断设计是否应该保留：

| 判断问题 | 保留标准 |
|---|---|
| 是否减少登录掉线、串店、重复登录 | 是则保留为硬约束 |
| 是否减少批量写操作重复执行、半途崩溃、失败不可追溯 | 是则保留为硬约束 |
| 是否让用户更快完成添加店铺、登录、预览、执行、导出 | 是则优先实现 |
| 是否能在平台接口变化后快速修复 | 是则保留为便利通道 |
| 是否只是安全审计需要，但不影响首个闭环 | 后置或降级 |
| 是否让 Gate 0 变成大平台工程 | 后置或拆分 |

分级说明：

| 等级 | 含义 | 处理 |
|---|---|---|
| SC-0 | 直接支撑稳定性或便利性 | 必须保留，进入当前 Gate |
| SC-1 | 有价值，但可轻量实现 | 保留合同，减少首版实现量 |
| SC-2 | 主要是安全化或平台化前置 | 后移 Gate，不阻断首个闭环 |
| SC-3 | 与便利性或稳定闭环冲突 | 修改设计方向 |

## 3. 源码事实摘要

### 3.1 Tianshe Runtime 与 Profile

`src/types/browser-runtime.ts` 显示 Tianshe 支持四种 Runtime：

```text
electron-webcontents
chromium-extension-relay
firefox-bidi
chromium-cloak-playwright
```

同文件还显示默认 Runtime 是 `electron-webcontents`，并且 `normalizeBrowserRuntimeId(undefined)` 或未知值会回退到默认 Runtime。这说明方案中“不能把空 runtimeId 透传给 Tianshe helper”的判断有代码依据。

`src/main/duckdb/profile-service.ts` 创建 Profile 时使用：

```text
partition = persist:profile-${id}
runtimeId = normalizeBrowserRuntimeId(params.runtimeId)
```

这说明 Tianshe Profile 本身就是稳定的浏览器凭据容器。一个店铺绑定一个 Profile 是稳定性底座，不是安全洁癖。

`src/main/duckdb/profile-row-mapper.ts` 读取数据库行时也会对 `runtime_id` 做归一化。也就是说，历史脏数据或空 runtime 可能在读取时被解释成 Electron 默认值。小尊宝自己的业务库需要保存 runtime 快照，避免用户不知道店铺实际跑在哪个 Runtime 上。

### 3.2 Runtime 能力差异

`src/core/browser-pool/runtime-capability-registry.ts` 显示：

| Runtime | 主要特点 | 对小尊宝的意义 |
|---|---|---|
| `electron-webcontents` | persistent、embedded-view、支持 cookies、DOM storage、截图、下载管理、页面输入；不持久化 response body | 首版登录和内嵌体验最方便 |
| `chromium-extension-relay` | persistent、external-window、支持 responseBody、tabs、intercept observe/control | 平台风控、接口响应体、页面注入需要时更强 |
| `firefox-bidi` | persistent、direct-window，能力多但多为实验 | 不适合首版默认 |
| `chromium-cloak-playwright` | persistent、external-window，需 managed download | 不适合首版默认 |

`src/main/ipc-handlers/account-ipc-handler.ts` 中登录弹窗也体现了体验差异：Electron Runtime 可以嵌入 popup，非 Electron Runtime 只能前置外部窗口。因此首版便利性优先时，Electron 应作为默认可用路径，而不是在 Runtime Spike 完成前完全阻断店铺登录。

### 3.3 Lease 自锁风险是真实存在的

`src/core/js-plugin/namespaces/profile.ts` 和 `profile-launch-namespace.ts` 明确说明：

```text
launchPopup() 会持续持有 profile live-session lease。
同一 profile 再发起 withLease() 会排队等待，看起来像界面卡住。
```

同时 `launchPopup()` 已经提供 `adoptSamePluginLockedBrowser()` 复用同插件已锁定 browser 的能力。方案中的 LoginSessionController 是必要设计，应该保留。它的目标不是安全，而是避免用户打开登录窗口后点击“检测登录”卡死。

### 3.4 插件页面是共享 WebContentsView

`src/main/webcontentsview-plugin-page-controller.ts` 显示 ActivityBar 插件页使用共享视图：

```text
SHARED_PLUGIN_PAGE_VIEW_ID = plugin-page:shared
SHARED_PLUGIN_PAGE_PARTITION = persist:plugin-page-shared
```

页面 API 由 `context.exposeAPI()` 注册后，再注入到 `window.pluginAPI[pluginId]`。`manifest.crossPlugin.exposedAPIs` 不会自动暴露 API。

这说明方案中“ActivityBar localStorage 不能作为店铺、登录、任务状态事实源”是正确的。但从便利性看，UI 仍可使用本地存储保存表格列、筛选条件、草稿、最近导出目录等可丢弃偏好。

### 3.5 数据库 helper 可以支撑 xzb_ 自管表

`src/core/js-plugin/namespaces/database.ts` 的 `executeSQL()` 在未传 `datasetId` 时会直接调用 `duckdb.executeSQLWithParams()`。传 `datasetId` 时才限定只读 SQL。

这说明使用 `helpers.database.executeSQL` 建立 `xzb_` 自管表可落地。方案选择不用 dataTables 承载核心任务状态是合理的。

### 3.6 旧小尊宝的便利性来源

旧小尊宝 V2.1.6 解包代码显示：

| 事实 | 源码位置 | 便利性作用 |
|---|---|---|
| 主窗口加载远程 `https://apptool.zzbtool.com` | `analysis_unpack/app_asar/dist-electron/main/index.js` | 业务页面可远程快速更新 |
| 主窗口 partition 为 `persist:myappzzbtool` | 同上 | 全局登录与页面状态复用方便 |
| preload 暴露 `window.client` | `analysis_unpack/app_asar/dist-electron/main/preload/index.js` | 远程页面可直接调用 cookie、http、db、窗口、下载 |
| 提供 `get_cookies/set_cookies/copy_cookies` | `work-server/cookie.js` | 登录态搬运和修复方便 |
| 提供 `http` 并写入 Set-Cookie 到 partition | `work-server/http.js` | 直接接口请求方便 |
| 提供 `_db/db` 本地存储 | `work-server/data_server/*.js` | 页面可快速保存任务和日志 |
| 插件请求 `plug*.zzbtool.com/zzbPlug/v3config` 并注入远程 JS/CSS | `plugin/正式版30.2.2/js/service-worker.js` | 平台页面增强和接口变化可快速热修 |

旧方案的问题不是“不方便”，而是太方便导致状态源太多、版本不可复现、远程变化不可控、Cookie 多处复制后容易失配。新方案不能简单把这些便利通道全部禁掉，否则会失去旧工具最有价值的迭代速度。更好的做法是保留便利入口，但让它们有本地兜底、缓存、版本固定和任务恢复。

## 4. 主要审计发现

### SC-01：Runtime Spike 不应阻断登录和只读验证

| 项 | 结论 |
|---|---|
| 分级 | SC-3 |
| 当前方案 | Gate 0 Runtime Spike 未完成前禁止创建新 Profile，禁止真实写入口 |
| 问题 | 这会把“添加店铺、人工登录、只读验证”也拖住，降低便利性 |
| 源码依据 | Tianshe 默认 Runtime 是 `electron-webcontents`，Profile 是持久 partition |

建议改为：

```text
Gate 0 可使用 electron-webcontents 创建 Profile、登录、做只读验证。
真实批量写操作仍要求 Runtime 通过最小验证。
如果 Electron 验证失败，引导用户新建 chromium-extension-relay Profile，不迁移凭据。
```

也就是说，Runtime Gate 应该是“写操作和默认推荐 Gate”，不是“所有店铺接入 Gate”。

### SC-02：一个店铺一个 Profile、一个 Profile 固定一个 Runtime 必须保留

| 项 | 结论 |
|---|---|
| 分级 | SC-0 |
| 当前方案 | 一个店铺绑定一个 Profile；Runtime 迁移必须新建 Profile |
| 判断 | 必须保留 |
| 原因 | 这直接减少串店、Cookie 失配、登录态搬运失败和 Runtime 混用问题 |

旧小尊宝和店汪汪都大量依赖 Cookie/token 搬运，这对便利性有帮助，但长期稳定性差。Tianshe Profile 已经提供持久登录仓，没有必要把 Cookie 复制成业务事实源。

补充建议：

```text
允许“新建 Runtime Profile 并重新登录”的迁移向导。
不做“复制 Cookie 到另一个 Runtime”。
UI 显示每个店铺当前 runtimeId、最后验证时间和 origin 状态。
```

### SC-03：Cookie 禁令应改成“Profile 为事实源，允许一次性便利桥”

| 项 | 结论 |
|---|---|
| 分级 | SC-1 |
| 当前方案 | 不保存 raw Cookie、token，不把 WebContents Cookie 搬给 HttpClient |
| 问题 | 对长期稳定是对的，但对下载、平台导出、少数接口会降低便利性 |

建议调整为：

```text
Profile browser storage 是唯一长期凭据事实源。
业务库不保存 raw Cookie/token。
允许 ProfileHttpService 或 DownloadService 在一次请求内临时读取 Cookie header。
允许用于平台文件下载、导出结果拉取、只读接口验证。
临时 Cookie 不跨店、不跨 Runtime、不持久化为店铺状态。
```

这不是为了安全让步，而是为了稳定和便利平衡：长期状态不复制，短期操作不绕远路。

### SC-04：LoginSessionController 是必要底座，不应裁剪

| 项 | 结论 |
|---|---|
| 分级 | SC-0 |
| 当前方案 | 统一管理登录弹窗、检测和释放 |
| 判断 | 必须保留 |
| 源码依据 | `launchPopup()` 持有 lease，同 Profile `withLease()` 会排队 |

建议把 Gate 1 的验收写得更偏用户体验：

```text
登录窗口打开时，点击“检测登录”复用当前 popup browser。
检测按钮 3 秒内有状态反馈，不能无提示等待资源锁。
关闭登录窗口后 handle 必须释放。
插件 reload 或应用退出后，下次启动能识别未释放状态并恢复。
```

### SC-05：xzb_ 核心状态表必须保留，但首版 migration 应收缩

| 项 | 结论 |
|---|---|
| 分级 | SC-1 |
| 当前方案 | 首版创建 shops、sessions、plans、jobs、partitions、items、attempts、artifacts 等 |
| 判断 | 核心表保留，周边诊断/更新/热规则表后置 |

首版必须保留：

| 表 | 原因 |
|---|---|
| `xzb_schema_migrations` | 升级稳定性 |
| `xzb_shops` | 店铺与 Profile 绑定 |
| `xzb_shop_origin_sessions` | 登录健康事实源 |
| `xzb_operation_plans` | 预览与确认 |
| `xzb_jobs` | 父任务恢复 |
| `xzb_job_shop_partitions` | 多店失败隔离，目标用户需要多店 |
| `xzb_job_items` | 单商品失败隔离 |
| `xzb_job_item_attempts` | 重试、未知结果和证据 |
| `xzb_artifacts` | 失败导出和诊断 |

可后置：

| 表/能力 | 建议 Gate | 原因 |
|---|---|---|
| `xzb_session_check_events` | Gate 2 | 初期可用结构化日志替代 |
| `xzb_plan_jobs` | Gate 3 后半或 Gate 5 | 大样本异步预览才需要 |
| 完整规则包表 | Gate 4/5 | 首个写功能前只需内置规则版本 |
| 更新历史表 | Gate 8 或运营发布阶段 | 不影响首个稳定闭环 |

### SC-06：JSON envelope 全覆盖会拖慢首版

| 项 | 结论 |
|---|---|
| 分级 | SC-2 |
| 当前方案 | 所有 JSON 字段都必须有 `{ schemaVersion, data }` |
| 问题 | 对 Gate 0 开发和调试成本偏高 |

建议：

```text
核心可演进 JSON 使用 envelope：input_json、preview_json、evidence_json、response_summary_json。
简单列表 JSON 可先使用约定字段和 repository 校验。
Gate 0 只检查关键 JSON 能读写、能迁移、能向后兼容。
不要让所有 JSON schema 测试阻断登录闭环。
```

### SC-07：预览、确认、Job/Item/Attempt 是稳定性，不是安全性

| 项 | 结论 |
|---|---|
| 分级 | SC-0 |
| 当前方案 | 写操作先 preview，再 confirm，再异步 job |
| 判断 | 必须保留 |

批量改标题、改价、删除、上下架、营销活动创建都可能造成大量不可逆或难恢复操作。预览、确认和 JobEngine 可以减少误操作、重复提交、崩溃半途不可恢复。这是稳定性底座。

但建议区分能力级别：

| 能力类型 | 处理 |
|---|---|
| 只读采集 | 不需要 confirm，直接 job 或同步查询 |
| 小样本低风险写 | 可 preview 后一键确认 |
| 批量写 | 必须 previewHash 确认 |
| 删除、彻底删除、营销创建 | typed confirm 或二次确认 |

### SC-08：ConfirmToken 设计过安全化，应以“不重复提交”为核心

| 项 | 结论 |
|---|---|
| 分级 | SC-2 |
| 当前方案 | confirmToken 绑定本机会话、5 分钟过期、保存 hash、提交后失效 |
| 问题 | 用户阅读大预览、暂停处理、切换窗口后容易过期，便利性差 |

建议简化：

```text
Plan confirmed 状态绑定 previewHash、inputHash、rulesVersion、endpointVersion。
submitJob 使用 planId + previewHash + submitIdempotencyKey 保证只创建一个 job。
confirmToken 可保留为实现细节，但默认有效期改为 30 分钟或跟随 plan expiresAt。
本机 session hash 不作为首版硬约束。
过期时 UI 提供“一键重新确认当前预览”，不要让用户重新生成全量预览。
```

稳定性真正需要的是：

```text
预览和提交一致
重复点击不会创建多个 job
崩溃恢复不会重复写
```

不是短期令牌本身。

### SC-09：远程 UI 和规则热更新不应一刀切禁止

| 项 | 结论 |
|---|---|
| 分级 | SC-3 |
| 当前方案 | 首版禁止远程 JS/CSS、规则包热更新、插件包自更新 |
| 问题 | 对安全有利，但会削弱平台接口变化后的修复便利性 |

旧小尊宝的主要便利来自远程 Web 和远程插件热更新。新方案不能回到“远程 eval 不可复现”的旧模式，但也不应该完全放弃热修能力。

建议采用“本地稳定壳 + 远程轻量配置”的折中：

```text
UI 主壳、本地 API、JobEngine、登录和写执行逻辑随插件包发布。
endpoint registry、错误码映射、字段路径、只读采集字段可支持远程 JSON 配置。
远程配置必须缓存 last-known-good。
配置拉取失败时使用内置版本，不影响应用启动。
每个 job 固定 rulesVersion、endpointVersion、configHash。
提供一键回退到内置规则。
```

如果确实要远程 UI，也建议只做：

```text
本地 ActivityBar 壳固定
远程公告、教程、轻量运营文案可加载
核心任务页面本地可用
远程不可用时不影响登录、执行和失败导出
```

这样服务的是稳定和便利，而不是安全边界。

### SC-10：完整首屏 API 合同过早

| 项 | 结论 |
|---|---|
| 分级 | SC-2 |
| 当前方案 | Gate 0 要求完整首屏 API 集合、UI API client 契约测试 |
| 问题 | 容易产生大量空实现和假完成 |

建议 Gate 0 只保留：

| API | 用途 |
|---|---|
| `getAppStatus()` | 插件版本、Tianshe commit、DB 状态、runtime 状态 |
| `listCapabilities()` | 只列当前启用和即将启用的能力 |
| `listShops()` | 店铺列表 |
| `createShopBinding()` | 新增店铺 |
| `openLogin()` | 打开登录 |
| `verifyLogin()` | 复用登录窗口检测 |
| `closeLogin()` | 关闭登录窗口 |

Gate 3/4 再加入：

```text
createPlan
getPlan
confirmPlan
submitJob
getJob
listJobItems
cancelJob
exportJobFailures
```

未启用 API 返回 `FEATURE_NOT_READY` 即可，不要要求完整成功路径。

### SC-11：MCP/跨插件限制不应成为 MVP 关注点

| 项 | 结论 |
|---|---|
| 分级 | SC-2 |
| 当前方案 | MVP 不开放 MCP 写操作，mcpCallable false |
| 判断 | 方向可以保留，但不应反复占据主方案篇幅 |

从稳定和便利角度，MCP/跨插件不是首个闭环的关键路径。保留默认关闭即可，不要让其测试、权限矩阵或审计阻断 Gate 0-4。

### SC-12：ActivityBar 共享 partition 需要 UI 缓存策略

| 项 | 结论 |
|---|---|
| 分级 | SC-1 |
| 当前方案 | UI storage 不能作为事实源 |
| 判断 | 正确，但可补便利说明 |

建议补充：

```text
允许 UI 使用 localStorage/IndexedDB 保存可丢弃偏好：
表格列宽、筛选条件、最近选择店铺、草稿输入、导出目录。
所有任务、登录、Profile、origin session、job 状态必须来自 xzb_ 表或 Tianshe Profile。
UI 缓存必须有 pluginId/key 前缀，避免共享 partition 下互相污染。
```

### SC-13：旧版 `window.client` 便利能力需要高层替代

| 项 | 结论 |
|---|---|
| 分级 | SC-1 |
| 当前方案 | 通过 Tianshe helpers 和 xzb API 分层 |
| 问题 | 如果只给严谨 API，不给便利封装，前端实现会变慢 |

建议在插件内提供“小尊宝便利 Facade”，但不暴露成随意系统能力：

| 旧小尊宝能力 | 新方案便利替代 |
|---|---|
| `window.client.http` | `ProfileHttpService.fetchJson()`、`fetchInPage()` |
| `window.client.downloadFileToPath` | `DownloadService.downloadWithProfileSession()` |
| `window.client.db/_db` | `XzbRepository` 和 `ArtifactService` |
| `executeJavaScriptBrowserWindow` | `SiteAdapter.evaluate()` |
| `get_cookies/copy_cookies` | 临时 cookie bridge，仅限当前 Profile 操作 |
| 远程插件注入 | Site Adapter procedure 或 extension relay fallback |

这样前端和业务开发仍然方便，但状态源不会像旧架构那样散。

## 5. 对主方案的修订建议

### 5.1 基线约束建议改写

当前“基线约束”建议修改为：

| 项 | 修订建议 |
|---|---|
| Tianshe 版本 | 保留，必须锁定 commit |
| 插件目录 | 保留 |
| 状态库 | 保留 xzb_ 表，但 migration 收缩到首个闭环 |
| Profile | 保留，一个店铺一个 Profile |
| Runtime | Profile 创建时必须记录显式 runtimeId；未 Spike 时可默认 Electron 做登录/只读，写操作需通过验证 |
| 高风险写操作 | 保留，写能力必须预览、确认、job |
| Cookie | 改为“Profile 为长期事实源，允许一次性便利桥” |
| 远程规则 | 改为“内置规则为兜底，远程 JSON 配置可作为热修通道” |
| UI API | 保留 context.exposeAPI，按 Gate 暴露最小 API |
| 发布更新 | 插件包自更新后置，但规则/endpoint hotfix-lite 可提前评估 |

### 5.2 Runtime 章节建议改写

建议把“Runtime 必须先验证再默认”改为：

```text
首版默认使用 electron-webcontents 作为登录和只读验证 Runtime。
Runtime Spike 用于确认真实写操作是否允许启用，以及是否需要为某类店铺推荐 chromium-extension-relay。
创建 Profile 时必须写入显式 runtimeId，不能传空值给 Tianshe。
如果 Electron 写验证失败，UI 提供“新建 Chrome Runtime Profile 并重新登录”向导。
不支持把已登录 Electron Profile 的凭据迁移到 extension relay。
```

验收重点：

```text
Electron 登录是否稳定
重启后登录态是否保持
Profile HTTP 只读接口是否可用
写前 freshness check 是否可用
失败时是否能引导用户切换 Runtime
```

### 5.3 规则与更新章节建议改写

当前方案把规则热更新完全后置。建议改成三层：

| 层级 | 内容 | Gate |
|---|---|---|
| 内置规则 | 随插件包发布，永远可离线运行 | Gate 0 |
| Hotfix Lite | 远程 JSON endpoint/字段/错误码配置，缓存和回滚 | Gate 2/4 |
| 插件包更新 | 完整 zip 更新、staging、版本替换 | Gate 8 |

Hotfix Lite 的稳定性要求：

```text
拉取失败不影响启动
新配置验证失败不激活
last-known-good 可继续使用
job 固定 configHash
用户可回退内置版本
```

### 5.4 安全策略章节建议降级为运行边界

第 17 章建议从“安全策略”改为“运行边界与便利通道”。其中保留对稳定有用的约束：

| 保留 | 降级 |
|---|---|
| Profile 为长期凭据事实源 | raw Cookie 绝对不可触碰 |
| 写操作必须 plan/job | confirmToken 复杂会话绑定 |
| endpoint host 有内置清单 | 远程配置绝对禁止 |
| artifact 不写无关敏感信息 | 全量脱敏扫描阻断 Gate 0 |
| MCP 写默认关闭 | MCP 矩阵审计阻断 MVP |

## 8. 对旧小尊宝能力的取舍

| 旧能力 | 便利性价值 | 稳定性问题 | 新方案取舍 |
|---|---|---|---|
| 远程 Web 主站 | 更新快 | 服务不可用则主功能不可用，版本不可复现 | 本地主壳，远程只做非核心内容或 JSON 配置 |
| 远程插件 JS eval | 平台页增强快 | 线上代码变化不可追踪，功能漂移 | Site Adapter 本地化，必要时 extension relay fallback |
| `window.client.http` | 接口调用方便 | 任意页面都能拼请求，状态难管 | ProfileHttpService 高层封装 |
| `get_cookies/copy_cookies` | 登录修复方便 | 多份 Cookie 失配、串 Runtime | 只允许当前 Profile 临时读取，不跨 Runtime 复制 |
| 本地 NeDB/SQLite 任意表 | 开发快 | 任务状态分散，恢复困难 | xzb_ repository 统一 |
| 隐藏窗口执行 JS | 适配平台方便 | 生命周期难控 | LoginSessionController 和 SiteAdapter 统一持有 |
| 失败日志导出 | 用户刚需 | 旧实现依赖页面临时状态 | ArtifactService 持久化 |

## 9. 最终建议清单

### 必须保留

- 一个店铺一个 Profile。
- 一个 Profile 固定一个 Runtime。
- Profile 是长期登录凭据事实源。
- LoginSessionController 统一管理 popup 和检测。
- xzb_ 自管核心状态表。
- 写操作 preview、confirm、submitJob。
- Job、Partition、Item、Attempt、Artifact。
- 崩溃恢复扫描。
- 单店、单商品失败隔离。
- 失败导出。

### 必须修改

- Runtime Spike 从 Gate 0 全阻断改为写操作 Gate。
- Cookie 绝对禁用改为允许一次性便利桥。
- ConfirmToken 从短期安全令牌改为提交幂等和预览一致性机制。
- 规则热更新从完全禁止改为 Hotfix Lite。
- 完整首屏 API 合同改为按 Gate 暴露。
- 安全策略章节降级为运行边界章节。

### 必须后置

- 插件包自更新和 staging。
- 完整规则包市场化。
- 全量 P2/P3 capability 目录。
- 全量 API contract test。
- 全量脱敏扫描阻断项。
- MCP/跨插件写操作治理。
- 复杂诊断事件表和完整诊断包。

## 10. 修订后的核心架构一句话

```text
Profile 管长期登录，LoginSessionController 管人工接管，ProfileHttpService 管便利请求，JobEngine 管恢复和失败隔离，RuleConfig 管内置兜底和热修版本，Artifact 管用户可用的导出结果。
```

## 11. 最终判断

v2.2 方案不是方向错误，而是“安全化阻断项”压得过前。按稳定性和便利性优先重新审计后，应该保留登录、Profile、Runtime 固定、JobEngine、预览确认、失败导出这些底座；同时放宽远程配置、临时 Cookie 桥、最小 API、Runtime 默认 Electron 登录等便利路径。

建议将主方案修订为 v2.3，核心目标改成：

```text
先交付一个真实可用、可恢复、少打扰用户的批量改标题闭环。
后续再把规则热修、插件更新、MCP、完整诊断和全量能力平台化补齐。
```

这会比当前 v2.2 更贴近本轮目标：稳定、方便、能上线、能快速修平台变化。
