# 小尊宝 2.0 基础底座建设方案审计报告

> 审计对象：`docs/小尊宝2.0基础底座建设方案.md`  
> 审计日期：2026-07-02  
> 审计目标：检查方案是否存在结构错误、冗余重复、无关内容、前后矛盾、后补痕迹，以及影响落地执行的关键缺口。  
> 审计结论：文档主方向已经调整为“自建新远程 Web 主站替换 `https://apptool.zzbtool.com`，旧站作为复刻参照和兼容基线”，但正文仍混有上一版“旧主站内灰度、不发壳包、不要求用户更新”的口径。当前版本不建议直接作为研发实施基线，应先修正 P0/P1 问题后再进入任务拆分。

## 1. 总体判断

这份方案的核心思路是成立的：

- 保留现有 Electron 本地能力层、`window.client` 合同、`persist:myappzzbtool`、Cookie/session、DB、窗口、日志和远程插件能力。
- 通过自建新远程 Web 主站承载旧主站复刻能力和猎狐 Shell。
- 新增能力通过 `liehuBridge` 做统一包装，避免新代码散落调用 `window.client`。
- 新增数据默认使用 `liehu20_` 命名建议，但不收窄旧 DB 能力。

但文档目前有三类主要问题：

1. **阻塞级结构问题**：存在多余 Markdown 代码围栏，导致后续章节渲染异常；章节编号也有明显断裂。
2. **核心决策口径未完全统一**：前文已经改成“替换远程 Web 主站”，后文仍保留“不发壳包”“不要求用户更新客户端”“远程主站新增 Shell”等旧说法。
3. **新域名替换旧域名的工程影响没有展开**：换 origin 会影响 Web Cookie、localStorage/IndexedDB、CORS、服务端白名单、插件跳转、回滚兜底和新站不可用时的启动路径，这些是当前方案最大的实操缺口。

## 10. 待确认问题

这些问题需要在修订前由产品/研发确认：

1. 新远程 Web 的正式域名是否确定？`https://www.liehu.com` 是正式域名、临时域名，还是文档占位符？
2. Phase 1 切换主站 URL 是否一定要发客户端包？如果要发，是否通过自动更新静默完成？
3. 如果用户不更新客户端，仍加载 `https://apptool.zzbtool.com` 的旧包如何处理？
4. 新主站是否需要复用旧站的 Web Cookie、localStorage 或 IndexedDB？
5. 旧主站登录态、用户信息、店铺信息的事实来源是什么？
6. 旧接口是否限制 Origin、Referer、CORS 或 Cookie Domain？
7. 远程插件是否有写死主站 URL？如果有，是改插件配置、做 redirect，还是保持旧域入口？
8. 新主站不可用时，是 DNS/CDN 回滚、客户端备用 URL，还是紧急入口包？
9. 是否能拿到旧远程 Web 源码？如果不能，是否允许仅基于线上产物和行为复刻？
10. Phase 1 保留 raw JS、raw URL、危险 DB 命令后，Phase 2 是否要补权限审计和调用台账？

## 11. 最终结论

这份方案已经具备正确的大方向，但当前不是一份“可直接执行”的稳定版本。最大问题不是内容不够，而是旧口径和新口径叠在了一起：

- 新口径：自建新远程 Web 主站替换 `https://apptool.zzbtool.com`。
- 旧口径：旧远程主站内灰度猎狐 Shell、不发壳包、不要求用户更新客户端。

建议先做一次“主线收敛”：只保留“新主站替换旧主站”的主线，把旧站内灰度的残留说法全部删除或改写；再补上新 origin 迁移、入口级回滚、插件跳转和旧站复刻验收。完成这些后，方案才适合作为研发拆任务和验收的依据。
