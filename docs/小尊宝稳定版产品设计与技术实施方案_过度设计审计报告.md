# 小尊宝稳定版产品设计与技术实施方案：过度设计审计报告

> 审计对象：`docs/小尊宝稳定版产品设计与技术实施方案.md`  
> 对象版本：v2.2 Gate 0 阻断修订版  
> 审计主题：是否存在过度设计，以及如何裁剪到首个稳定闭环  
> 审计日期：2026-06-29  
> 审计结论：存在局部过度设计，但不是整体架构方向错误

## 1. 总体结论

当前方案的主线是成立的：它不是为了“架构漂亮”而堆模块，而是在解决旧工具类产品最容易出事故的几个问题：登录态不稳定、Cookie 搬运、批量写操作重复执行、崩溃后无法恢复、敏感数据进入日志和导出物、宿主 Runtime 行为不确定。

因此，方案中的稳定性底座不能简单按“复杂”裁掉。尤其是 Profile 凭据隔离、Runtime Spike、compatibility adapter、预览确认、JobItem/Attempt、恢复扫描、脱敏边界，属于稳定版必须付出的复杂度。

但文档确实存在局部过度设计，主要表现为：

1. Gate 0 阻断项偏多，把部分 Gate 3、Gate 4、Gate 8 才需要完整实现的能力前置了。
2. P2/P3 功能虽然标了阶段，但目录结构、Capability 元数据和逐功能规格容易被误读为首版工程范围。
3. 首版 migration 一次性放入了更新、规则热更新、诊断事件、大样本预览等未来能力表。
4. API 和 Capability 合同偏向一次性完整平台化，可能导致空实现、空测试和伪完成。
5. 更新体系设计正确但工程时机过早，尤其是 host update adapter 和插件包 staging 安装不应影响 MVP 闭环。

建议采用“保留安全底座，推迟平台化能力”的裁剪策略。也就是说，不要砍掉任务恢复和写操作确认，但要把更新发布、P2/P3、完整 Capability 超集、全量 API 和部分审计表后置。

## 2. 审计分级说明

| 等级 | 含义 | 处理方式 |
|---|---|---|
| OD-0 | 必要复杂度，不属于过度设计 | 保留，补足验收证据 |
| OD-1 | 轻微超前，但成本可控 | 保留为合同或占位，不要求完整实现 |
| OD-2 | 明显超前，会增加首版工程量 | 从当前 Gate 移出，延后实现 |
| OD-3 | 高成本且短期无收益 | 删除、改 Spike 或改待确认问题 |
| OD-4 | 与目标冲突或制造错误安全感 | 必须修订 |

## 3. 必须保留的稳定性底座

| 设计项 | 分级 | 结论 | 理由 |
|---|---|---|---|
| 单插件承载首版 | OD-0 | 保留 | 16 个功能共享登录、任务、规则、失败导出和状态模型；首版拆插件会增加一致性风险 |
| Profile 是唯一凭据容器 | OD-0 | 保留 | 防止 Cookie/token 搬运、跨店串凭据和敏感泄露 |
| Runtime Spike | OD-0 | 保留 | 写操作和登录稳定性依赖 Runtime 行为，不能靠文档假设 |
| compatibility-adapter | OD-0 | 保留 | Tianshe helper 和类型存在不确定性，需要收窄产品语义 |
| 高风险写操作预览确认 | OD-0 | 保留 | 批量改标题、改价、删除、营销创建都需要防误操作和防重复提交 |
| Job / Item / Attempt | OD-0 | 保留 | 支撑失败隔离、崩溃恢复、unknown_result 和证据链 |
| confirmToken 绑定 previewHash | OD-0 | 保留 | 防止预览和实际提交不一致 |
| 脱敏 DTO 和数据库错误脱敏 | OD-0 | 保留 | Tianshe observation、日志、artifact 都可能泄露敏感信息 |
| Profile HTTP Spike | OD-0 | 保留 | 写操作必须先证明能在 Profile origin 内稳定请求 |
| 失败导出 artifact | OD-0 | 保留 | MVP 闭环明确要求失败项导出 |

这些内容看起来重，但它们直接对应真实事故类型，不建议裁剪。

## 5. Gate 裁剪建议

### 5.1 Gate 0：工程和依赖准备

原方案 Gate 0 偏重，建议收窄为“不开工会出错”的内容。

| 保留为阻断项 | 后置或降级 |
|---|---|
| 插件骨架、manifest、构建和打包脚本 | 完整 RuleService 验签骨架后置到 Gate 4/8 |
| Tianshe commit lock | `xzb_update_history` 后置到 Gate 8 |
| Runtime Spike 报告 | `xzb_rule_packages` 热更新表后置 |
| compatibility-adapter 最小合同 | 完整首屏 API 集合改成最小 API 集合 |
| manifest validator：local source、path 不越界、runtime 不空传 | 所有 API 成功路径测试按 Gate 后置 |
| migration runner 最小能力 | P2/P3 目录和 handler 不创建 |
| `xzb_schema_migrations` 最小表 | 完整更新验收不属于 Gate 0 |
| API 注入 smoke test：`getRuntimeStatus` 可调用 | 大样本 plan job 可先不启用 |
| 数据库错误脱敏 fixture | 规则包远程下载和热更新不阻塞 |

建议 Gate 0 退出条件改为：

1. 插件可安装、可加载、UI 可打开。
2. Tianshe commit 已锁定。
3. Runtime Spike 完成，未通过时真实写入口关闭。
4. adapter 拒绝空 runtimeId 和非法 Runtime。
5. migration runner 能创建最小表并重复执行。
6. ActivityBar 页面能调用 `getRuntimeStatus()` 和 `listCapabilities()`。
7. manifest validator 和错误脱敏 fixture 通过。

### 5.2 Gate 1：店铺登录闭环

Gate 1 基本合理，建议只控制事件表和多 origin 范围。

| 保留 | 调整 |
|---|---|
| ShopService、LoginSessionController、LoginService | `xzb_session_check_events` 可选，不要阻塞登录闭环 |
| `xzb_shops`、`xzb_shop_origin_sessions` | compass、buyin 可记录 unknown/pending，不强制全部真实验证 |
| 店铺管理 UI | 订购状态、功能包状态后置 |
| 无 popup lease 自锁验收 | 登录诊断包可后置 |

### 5.3 Gate 2：Profile HTTP 和错误分类

Gate 2 是首个真实写闭环的关键前置，建议保留。

| 保留 | 调整 |
|---|---|
| Profile HTTP Spike | 不引入完整 endpoint 热更新 |
| endpoint registry 最小只读商品详情 | 先使用内置 endpoint 配置 |
| response-classifier | 错误码映射允许最小集 |
| evidence 脱敏 | artifact screenshot 可按失败场景后置 |
| per-origin 队列 | 跨 compass/buyin 的完整能力后置 |

### 5.4 Gate 3：持久 JobEngine

Gate 3 是必要复杂度，但可以做“单能力最小 JobEngine”。

| 保留 | 调整 |
|---|---|
| OperationPlan、Job、Item、Attempt | `JobShopPartition` 若首个验收只做单店，可先弱化使用 |
| confirmToken 消费 | 大样本 `createPlanJob` 可先按阈值启用 |
| RecoveryService 最小恢复扫描 | 复杂并发 worker pool 后置 |
| ArtifactService 失败导出 | 首版优先 CSV，Excel 可后置 |
| 任务中心 UI | 复杂筛选和批量重试后置 |

### 5.5 Gate 4：首个真实写功能

Gate 4 选择批量改标题是合理的。建议把它作为 Capability 模板的唯一完整样板，而不是同时铺开 P1 全套商品能力。

| 保留 | 调整 |
|---|---|
| `goods.title.preview` / `goods.title.execute` | 其他 P1 能力不进入 Gate 4 |
| 标题规则测试向量 | 规则热更新不阻塞，可用内置 rulesVersion |
| previewHash、写前再校验 | 完整规则包签名可后置到 Gate 8，Gate 4 保留规则 hash |
| 重复提交不重复写 | 多店大规模压测后置到 Gate 5 |
| 失败导出 | Excel 可后置，CSV 必须保留 |

## 8. Capability 合同裁剪建议

当前 `XzbCapability` 把读能力、写能力、采集能力、营销能力的字段放进一个大结构，长期会导致每个 capability 都要填无意义字段。

建议改为分层：

```ts
type BaseCapability = {
  name: string
  title: string
  version: string
  phase: "P0" | "P1" | "P2" | "P3"
  inputSchema: object
  outputSchema: object
  requiredOrigins: Array<"fxg" | "compass" | "buyin">
  sideEffectLevel: "none" | "low" | "medium" | "high" | "destructive"
}

type WriteCapability = BaseCapability & {
  previewItemSchema: object
  jobItemPayloadSchema: object
  confirmPolicy: "preview" | "typed_confirm"
  idempotencyKeyTemplate: string
  reconcileStrategy: "read_after_write" | "list_and_match" | "manual"
}

type CollectCapability = BaseCapability & {
  fieldSourceSchema: object
  exportSchema: object
  partialFailurePolicy: "keep_metric" | "skip_metric" | "skip_shop"
}
```

Gate 4 只需要把 `goods.title.preview / goods.title.execute` 做成第一个完整 `WriteCapability` 样板。P2/P3 能力只保留路线图，不要求补齐所有 fixtures、rateLimit、reconcile 策略。

## 9. 更新和规则体系裁剪建议

### 9.1 插件更新

原方案对“插件不得自覆盖、必须依赖 host adapter”的判断是正确的，但实现时机应后置。

建议：

1. Gate 0 不实现插件包更新。
2. Gate 0 只校验 manifest 本地 source、安全路径和 runtime 不空传。
3. Gate 8 前，`checkForUpdates()` 不应进入安装模式。
4. 如果 UI 需要显示版本，可只提供 `getRuntimeStatus()` 中的 pluginVersion。
5. `xzb_update_history` 移到 Gate 8 migration。

### 9.2 规则版本

规则版本固定是必要的，规则热更新不一定首版必要。

建议：

1. Gate 4 前使用内置规则包或内置 endpoint registry，记录 `rulesVersion`、`endpointVersion` 和 hash。
2. `submitJob` 固定规则版本的要求保留。
3. 远程规则包验签、激活、retire、`xzb_rule_packages` 可延后。
4. 如果必须首版远程修规则，则只允许 JSON 配置，不允许 JS、任意 URL 或任意 host。

## 11. P2/P3 范围控制建议

文档中的 16 个功能追踪矩阵有价值，但应明确它是产品路线，不是首版实现范围。

建议增加一句约束：

```text
P2/P3 章节只作为路线图和后续 Capability 填写依据，不进入 Gate 0-4 的代码目录、测试矩阵和 migration 阻断项。除非某字段被 Gate 4 的 goods.title 首个写闭环复用，否则不得提前实现。
```

同时建议目录结构从“全量目录”改成“增量目录”：

```text
src/
  capabilities/
    registry.ts
    shop.ts
    goods-title.ts
  engines/
    goods-title-engine.ts
  site/
    douyin_fxg/
      endpoints.ts
      verifiers/
```

等 Gate 5 后再补 `goods-price`、`freight` 等能力，Gate 6/7 再补 metrics、marketing、stale-goods。

## 12. 建议修订后的 Gate 0-4 路线

| Gate | 目标 | 最小交付 | 不进入本 Gate |
|---|---|---|---|
| Gate 0 | 宿主合同和工程底座 | 插件骨架、manifest validator、commit lock、Runtime Spike、adapter、最小 migration、API smoke、脱敏 fixture | 更新发布、规则热更新、P2/P3 目录、全量 API |
| Gate 1 | 店铺登录闭环 | 店铺绑定、Profile 创建、人工登录、登录检测、origin session、无 lease 自锁 | 订购状态、完整诊断事件、全部 origin 深度能力 |
| Gate 2 | Profile HTTP 可用性 | 只读商品详情、endpoint 最小 registry、错误分类、origin 串行队列、Profile HTTP Spike | 远程 endpoint 热更新、营销/数据采集 endpoint |
| Gate 3 | 最小持久任务 | plan、confirmToken、job、item、attempt、恢复扫描、任务中心、CSV 失败导出 | 大样本 plan job 强制实现、复杂 worker pool、Excel |
| Gate 4 | 首个真实写功能 | 批量改标题 preview/execute、写前校验、规则 hash、重复提交保护、小样本真实验收 | 全 P1 商品能力、规则热更新、插件更新 |

## 13. 对主方案的具体修改建议

建议在主方案中做以下修改：

1. 在第 5.1 目录前增加说明：目录是最终建议形态，Gate 0-4 只创建当前需要的子目录。
2. 在第 6 章增加“首版最小 migration”和“后续 migration”拆分，不把所有表都塞进 `001_initial`。

## 14. 最终判断

本方案存在局部过度设计，严重程度为中等。它的问题不是“稳定性设计太多”，而是“未来平台能力进入首版工程面太早”。

保留底座：

- Profile 凭据隔离。
- Runtime Spike 和 adapter。
- 高风险写操作预览确认。
- Job / Item / Attempt / 恢复。
- 脱敏 DTO、错误脱敏和 artifact。
- Profile HTTP Spike。

建议裁剪：

- 插件更新发布实体化。
- 规则包热更新完整表和流程。
- P2/P3 能力提前代码化。
- Capability 超集接口。
- 全量 API 提前注册和全量 contract test。
- `xzb_update_history`、可选 `xzb_rule_packages`、可选 `xzb_session_check_events` 前置建表。

一句话结论：

```text
这份方案应该从“全产品稳定平台蓝图”收缩为“首个真实写闭环的稳定底座”。稳定底座不能砍，平台化和未来能力要后置。
```
